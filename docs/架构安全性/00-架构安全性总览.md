# 架构安全性

> 本专题以《凤凰架构》开源文档的“架构安全性”章节为基础。认证、授权、凭证、保密、传输、验证六篇保留原版正文，并在文末单列“现代实践补充”；其余篇章均为扩展内容。这样的边界既保留原作的叙事，也避免读者把后来补充误认为原文。

安全不是某个网关、WAF 或身份服务的功能，而是系统在身份、数据、代码、基础设施和运营全过程中的约束。架构安全的目标也不只是“防止被黑”，还要同时保护：

- **保密性**：信息只对获得授权的主体可见。
- **完整性**：数据、代码和控制指令的来源与内容可信。
- **可用性**：系统面对故障、攻击和误操作仍能提供必要服务并恢复。
- **真实性与可追责性**：主体、操作和证据能够被可靠验证与审计。
- **隐私与安全使用**：数据的收集和使用符合目的、边界与用户预期。

本专题的内容组织改进计划见[架构安全性内容组织改进建议](架构安全性内容组织改进建议.md)。它用于解释为什么后续章节会逐步补充学习目标、贯穿案例、决策表和验收证据。

## 能力地图

“零信任”不是单独一层产品，而是贯穿这些能力域的设计方式：不因网络位置默认信任；每次访问都基于可验证身份、最小权限、资源和上下文做判断；假设凭证、终端或服务可能已被攻破，并限制爆炸半径。

## 贯穿案例

为了避免读者把安全控制理解成孤立知识点，后续内容可以始终带着一个“多租户订单系统”的案例来阅读：普通用户下单和支付，运营人员按租户导出订单，管理员维护账号和权限，系统通过消息处理异步任务，并把日志、备份、分析数据和第三方回调纳入架构边界。

这个案例足够普通，却能同时暴露典型安全问题：用户是谁，运营能看哪些租户，订单导出是否越权，下载文件保存多久，支付回调能否重放，CI/CD 能否接触生产秘密，备份能否恢复，日志能否追责，数据注销后副本如何删除。每章都可以回到这个系统中，回答“本章控制解决了哪一段风险”。
