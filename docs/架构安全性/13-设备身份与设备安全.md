# 设备身份与设备安全

> 返回《[架构安全性](00-架构安全性总览.md)》目录。本文是可选的现代扩展，适用于 IoT、嵌入式终端、边缘节点、工业控制终端以及其他可能离线或被物理接触的设备。

假设一把智能门锁首次联网时向云端提交序列号 `SN-10086`，云端在设备表里找到这条记录，便认为它是合法产品。攻击者从包装盒上拍到了序列号，在自己的开发板上发送同样请求，也被识别成了这把门锁。

问题并不在于序列号是否足够随机，而在于系统把“标识”误当成了“身份证明”。设备 ID 回答云端应该查找哪条记录，设备凭证证明请求者确实持有登记设备的秘密，所有权描述设备当前属于哪个用户或组织，授权再决定主体可以开锁、查看状态还是修改配置。这四个概念若搅在一起，设备转让、密钥轮换和权限撤销都会变得异常困难。

## 一台设备如何证明“我是我”

服务器可以随时从身份平台取得短期凭证，设备却可能要运行十年，长期离线，部署在攻击者可以拆开外壳的位置。把同一份产品级密钥烧录进整个批次最省事，但只要一台设备被拆解提取密钥，攻击者就能克隆整个产品系列，云端也无法单独撤销其中一台。

现代设备身份通常建立在每台设备独有的非对称密钥上。私钥优先在设备内部生成，保存在安全芯片、TPM、TEE 或具备防提取能力的区域；云端登记公钥或由受信任 CA 签发证书。连接时，云端给出随机挑战，设备用私钥签名，或者双方通过 mTLS 完成认证。序列号仍可用于定位记录，却不再承担秘密的职责。

硬件保护增强的是“这把私钥很可能仍在那台设备里”，并不能证明设备当前属于谁，更不能决定它能开哪扇门。云端还要把设备身份映射到明确权限，并维护激活、冻结、退役、凭证版本和产品安全状态。

## 身份最初从哪里来

所有后续认证都依赖第一次登记。如果攻击者能够抢在用户之前注册设备，再强的运行证书也只是在可靠地证明“一台被绑定给错误用户的真设备”。

设备通常带着受限的出厂身份离开生产线。首次联网时，它用出厂私钥完成挑战，云端检查产品、批次和吊销状态，再使用一次性、短有效期的注册凭证加入目标环境。注册完成后，目标环境签发权限更小、可轮换的运行身份，出厂身份只保留为重新建立信任所需的根，而不直接承担日常业务访问。

这条链路的安全从生产环节就开始了。产线如果集中保存所有设备私钥，数据库泄漏会变成全量克隆；若必须注入私钥，就要隔离设备、加密传输并审计每次操作。更理想的方式是在设备内部生成私钥，只把公钥送出。测试与生产的设备 CA、固件签名密钥和业务密钥也要分离，避免测试证书天然进入生产。

## 设备认证与用户绑定是两次证明

回到智能门锁场景。门锁通过签名证明它是真设备以后，用户还要证明自己有权接管它。一次性二维码、近场通信、设备上的物理按键或可信安装人员，都可以为“设备就在用户手边”提供额外证据。单凭可拍照的序列号远程绑定，最容易产生抢先注册。

所有权关系不适合直接写入长期设备证书。房屋出售后，门锁的硬件身份没有变化，所有者和权限却要整体更换。如果两者分离，转让只需撤销旧用户的授权和会话，清除本地数据，再建立新绑定，无需重写设备根身份。

敏感控制指令还要防止重放。有效签名只能证明消息曾由某个密钥签发，攻击者录下一条“开锁”命令后仍可能重复发送。时间可靠的设备可以校验时间戳和唯一消息 ID，时钟不可靠的离线设备则可使用服务端挑战、单调计数器或受控窗口。请求中的设备 ID 必须从已经验证的证书映射，不能一边验证 A 设备的证书，一边相信正文声称自己是 B 设备。

## 安全启动解决的是哪一段信任

设备即使持有正确私钥，运行的也可能已经是攻击者替换的固件。安全启动从芯片内部的不可变根公钥开始，逐级验证引导程序、操作系统和应用镜像的签名与版本。任一环节失败，设备进入受限恢复模式，而不是继续执行来源未知的代码。

签名证明固件来自授权发布者且没有在传输中被修改，并不证明固件没有漏洞。因此安全启动必须配合最小化组件、运行隔离、漏洞治理和安全更新。度量启动与远程证明可以进一步向云端报告当前加载的组件，但云端不能相信设备自行上报的哈希；证明必须由可信硬件签名并绑定本次挑战，否则只是一份容易伪造的自我声明。

## OTA 为什么比“下载后重启”复杂

设备的预期寿命通常远长于初始固件的安全寿命，可靠更新能力本身就是核心安全控制。更新包要验证签名、产品型号、硬件版本和发布通道，版本策略要阻止攻击者把设备降级到仍有有效签名但已知脆弱的旧版本。

更新服务与固件签名服务应分权。取得发布账号的人可以安排某个已签名版本上线，却不应同时取得离线根私钥签署任意固件。A/B 分区、恢复镜像或事务式更新用于处理断电和写入失败；灰度、暂停和成功率监控则防止一份有缺陷但签名完全正确的固件同时损坏全部设备。

防回滚与可恢复之间存在真实矛盾。严格拒绝旧版本能够阻挡降级攻击，却可能在新版本故障时失去救援路径。通常会预先定义仍被授权的安全回退版本，紧急恢复只能退到这个集合，而不是关闭签名验证或接受任意历史镜像。

## 物理接触改变了哪些假设

服务器架构常假设攻击者不能直接探测内存总线，设备却可能被买回家慢慢拆解。量产版本应关闭不需要的服务、测试账号和调试功能；JTAG、UART、SWD、ADB 等接口应关闭、加锁或通过受审计的授权流程临时解锁。维修模式不能绕过安全启动和云端授权，也不能暴露整个产品系列共用的密钥。

本地存储中的用户数据、Wi-Fi 凭证和运行身份需要加密并限制进程访问，日志不能留下私钥、默认口令和完整 Token。USB、蓝牙、近场通信和本地 Web 管理页都是真实入口，应按产品实际需要保留最小功能。无法抵抗高成本实验室攻击并不代表可以忽略低成本的调试口读取；控制强度应与设备价值和部署环境匹配。

## 一台设备怎样结束生命

解除绑定、恢复出厂和退役并不是同一个动作。解除绑定撤销用户关系但可以保留设备根身份；恢复出厂清除用户数据、运行凭证和配置，同时保留重新建立可信身份所需的最小材料；退役则吊销设备身份、清除本地秘密并把云端资产状态永久关闭。

设备无法立刻联网时，实时吊销不会马上生效。可以结合短期运行证书、周期续期、拒绝列表和重新入网检查缩短风险窗口。无法可靠擦除存储时，销毁加密密钥可以让残留密文不可恢复。云端还应维护设备版本、最后连接、认证失败、调试状态、更新结果和支持期限，以便在某个产品漏洞出现时回答“哪些设备受影响、哪些仍未修复”。

设备安全最终是一条从生产、注册、运行、更新到退役的信任链。只给 API 加上 mTLS，或只给固件加一个签名，都保护不了这条链上其他没有被认真定义的环节。

进一步的通用能力基线可参考 [NISTIR 8259A](https://csrc.nist.gov/pubs/ir/8259/a/final)。
