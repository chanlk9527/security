# 密钥与秘密管理

> 返回《[架构安全性](00-架构安全性总览.md)》目录。本文是现代扩展。用户密码见[保密](05-保密.md)，令牌见[凭证](04-凭证.md)，证书与 TLS 见[传输](08-传输.md)。

假设某个应用需要连接数据库。最直接的做法是在配置文件里写入用户名和密码；为了避免提交到源码，又把它改成环境变量；随后容器平台再把环境变量的值保存在 Secret 对象中。秘密的存放位置换了三次，但根本问题并没有消失：谁能够读取它，它能访问什么，泄漏后如何更换，以及旧值还能使用多久？

秘密管理不是寻找一个“绝对看不见的字符串存放处”，而是管理一份能够代表身份或解开数据的权力。

## 先区分秘密、密钥与凭证

工程里常把数据库密码、API Key、私钥、Token、证书和恢复码都叫做“密钥”，但它们承担的安全职责并不相同。秘密是需要防止未授权读取的值；密钥是参与密码学运算的秘密或公私钥材料；凭证则是主体向系统证明身份或权限的证据。一个 OAuth Access Token 可能不参与加密，却能调用接口；一把 AES 密钥不能证明身份，却能解开数据；一张 TLS 证书包含公钥和身份绑定，真正需要保护的是与它匹配的私钥。

这种区分会影响解决方案。能够重新签发的短期访问凭证，重点是缩短有效期和快速撤销；长期加密密钥，重点是隔离、版本、算法迁移和数据可恢复性；第三方 API Key，重点是最小权限、来源限制、配额和泄漏检测；恢复码和 Break-glass 账号，重点是离线保存、双人控制和事后审计。把所有东西都塞进同一个 Secret Manager，并不能自动得到同一种安全性。

设计时可以先问五个问题：这份秘密代表谁，能做什么，在哪里被创建和使用，泄漏后多大范围受影响，多久可以撤销或自然失效。回答不清楚时，先不要讨论用哪个产品保存它，因为真正缺失的不是保险箱，而是权力边界。

## 从具体场景看风险

第一类场景是应用访问基础设施。订单服务需要连接数据库、缓存、消息队列和对象存储。如果每个服务共享同一个高权限账号，一次容器逃逸或日志泄漏就可能变成全库读写。更合理的方式是按服务、环境和用途拆分身份，例如生产订单服务只能访问生产订单库的必要表和必要动作，报表服务只能读取经过授权的数据视图，迁移任务使用有到期时间的临时高权限凭证。这样即使某个凭证泄漏，攻击者得到的也是受限能力。

第二类场景是 CI/CD 与供应链。构建流水线通常需要拉取依赖、推送镜像、发布云资源和更新配置。若把云账号长期 Access Key 保存在流水线变量里，任何能修改构建脚本的人都有机会把它打印、外传或用于横向移动。更好的方案是让 CI 平台通过 OIDC、工作负载身份或受限 Runner 向云平台换取短期部署凭证，并把部署权限限制到特定仓库、分支、环境和审批状态。构建环境不应接触生产运行时秘密，生产部署也不应依赖开发者本机保存的私钥。

第三类场景是系统间回调。Webhook 签名密钥常用于证明请求确实来自合作方。它的问题不在于值有多长，而在于验证方是否校验时间戳、请求体、算法、Key ID 和重放窗口。一个没有时间戳的 HMAC 签名，即使密钥没有泄漏，也可能被攻击者原样重放；一个没有 Key ID 的签名方案，轮换时也很难判断该用新密钥还是旧密钥验证。

第四类场景是数据加密。数据库透明加密可以保护丢失磁盘和备份，但应用查询时仍会看到明文；字段级加密能缩小 DBA、分析账号和备份泄漏的影响，但也引入查询、索引、轮换和权限判断的复杂度。加密不是一个开关，而是对“谁可以在什么边界内获得明文”的重新设计。

第五类场景是人类应急访问。生产事故中可能需要工程师临时查询数据、重启服务或执行修复脚本。若平时大家共用一套管理员密码，既无法追责，也无法在人员离职或外包结束后精确撤销。应急权限应当是实名、限时、审批、可审计的，并且只在正常自动化无法完成时使用。

## 静态秘密为何越来越难管理

数据库密码、第三方 API Key、OAuth 客户端秘密、Webhook 签名密钥、TLS 私钥、JWT 签名密钥、云访问密钥和恢复码的用途各不相同，却有一个共同特点：得到它的人通常就获得了它代表的能力。

静态秘密在分布式系统里会不断复制。部署系统需要一份，运行实例需要一份，排障脚本可能又保存一份；轮换时还要确保所有副本同时更新。只要一个旧实例或遗忘的定时任务仍依赖旧值，管理员便不敢真正撤销它，所谓“每九十天轮换”最终常常只是生成了更多长期有效的秘密。

业界更倾向于先证明工作负载身份，再由秘密管理服务按需签发短期凭证。云平台、Kubernetes 或 SPIFFE 一类工作负载身份体系，可以根据运行环境确认“这是生产环境中的订单服务”，数据库或云服务再授予它有限时间、有限资源的权限。这样，部署过程不必搬运一个永久密码，实例退役后凭证也会自然过期。

这并不意味着所有环境变量都不安全，而是环境变量只解决了“不把值写进普通配置文件”，没有防止同进程读取、调试工具、崩溃转储和过宽权限。它是一种交付手段，不是一套完整的秘密生命周期。

Kubernetes Secret 也要放在同样的位置理解。它默认只是把值以对象形式交给集群管理，并不等于只有目标容器能看见，更不等于应用内存、日志、调试接口和节点磁盘都安全。要让它成为可靠控制，还需要启用静态加密、收紧 RBAC、限制 ServiceAccount Token、隔离命名空间、保护节点和控制面，并避免把 Secret 直接展开到会被错误采集的日志或诊断输出里。

## 生命周期比存放位置更重要

一项秘密从产生到销毁，通常会经过创建、登记、分发、加载、使用、轮换、撤销、销毁和审计几个阶段。任何阶段失控，都会削弱前面所有努力。

创建阶段要保证随机性和唯一性。API Key、对称密钥和恢复码应由密码学安全随机数生成器产生，不应由时间戳、用户名、短 UUID 或业务流水号拼接。非对称密钥要选择当前仍被接受的算法和长度，并记录用途、环境和到期策略。

登记阶段要让秘密成为资产，而不是散落的字符串。至少应记录所有者、用途、环境、权限范围、使用方、创建时间、到期时间、版本、轮换频率、紧急联系人和撤销步骤。没有所有者的秘密，最后一定会变成没人敢删的遗留权限。

分发阶段要尽量避免人手搬运。开发环境可以通过个人身份临时获取低权限测试凭证；CI/CD 通过平台身份换取部署凭证；线上工作负载通过实例身份、ServiceAccount、mTLS 或 SPIFFE ID 换取运行凭证。复制到聊天软件、工单备注、个人网盘和本地脚本里的秘密，基本都会逃离生命周期管理。

加载和使用阶段要减少明文驻留。应用应按需读取，避免把完整秘密打印到启动日志、错误栈、指标标签和审计字段中。内存并不是绝对安全边界，但减少副本仍然有价值：副本越少，崩溃转储、调试接口、Sidecar、插件和依赖库误读的机会越少。

撤销和销毁阶段要验证结果。删除 Secret Manager 里的旧版本，不代表所有客户端已经停止使用，也不代表第三方平台已经拒绝旧值。系统应能观察旧版本是否仍被调用，能在紧急情况下强制拒绝，并能确认备份、镜像、制品、日志和历史提交中的泄漏副本不会继续产生能力。

## 常见方案如何组合

秘密管理服务负责集中保存、分发、审计和轮换普通秘密，例如数据库密码、API Key、OAuth 客户端秘密和 Webhook 密钥。它的核心价值不是“数据库更结实”，而是把秘密从源码、镜像和配置仓库中移出，并让读取行为具备身份校验、访问策略、版本和审计。

KMS 负责提供受控的密码学能力，例如生成数据密钥、加解密小块密钥材料、签名、验签和密钥版本管理。业务系统最好不要导出高价值根密钥，而是把加密或签名请求发送给 KMS。这样能减少明文密钥副本，并把“谁在什么时候使用哪把密钥做了什么运算”变成可审计事件。

HSM 是更强的硬件隔离边界，常用于支付、证书颁发、根密钥、监管要求或极高价值签名场景。它并不神奇，仍然需要权限、流程和审计配合；但它能让密钥材料在物理和固件边界内生成、保存和使用，使导出私钥变得不可行或需要受控仪式。

工作负载身份解决“谁来取秘密”的问题。云实例角色、Kubernetes ServiceAccount、mTLS 证书和 SPIFFE ID 都是在让平台为运行中的程序背书。秘密管理服务再基于这个身份签发短期数据库凭证、云访问凭证或服务调用凭证。它把“在部署时塞入永久密码”改成“在运行时按身份换取有限权力”。

策略引擎和权限系统解决“取到以后能做什么”的问题。即便服务能够读取某个数据库密码，也不应因此拥有跨环境、跨租户和跨业务域的能力。密钥策略、数据库角色、云 IAM、网络策略和应用授权需要共同收敛到最小权限。

## 一次可执行的轮换

真正的轮换不是在密钥库里点一下“生成新版本”。以签名密钥为例，如果签发方立刻改用新私钥，而验证方还没有取得新公钥，所有新令牌都会失效；如果验证方永远保留旧公钥，泄漏的旧私钥又可以继续伪造凭证。

可靠顺序通常是先让验证方同时认识新旧密钥，再让签发方切换到新密钥，等待旧凭证越过最长有效期，最后停止信任并销毁旧密钥。数据库密码、Webhook 密钥和数据加密密钥虽然细节不同，也都需要一段受控的双版本窗口。每项秘密因而要有所有者、用途、使用者、版本、到期时间和紧急撤销步骤，而不只是一个值。

高价值根密钥和签名密钥通常放入 KMS 或 HSM，使私钥运算在受控边界内完成而不是导出明文。这里的收益不仅是“硬件更安全”，更重要的是集中权限、审计和轮换，并减少密钥副本。KMS 管理员也不应天然拥有使用所有业务密钥解密数据的权力，管理密钥与使用密钥需要职责分离。

不同秘密的轮换剧本不同。数据库密码常见做法是准备两个账号或两个密码版本：先创建新凭证并授予等价最小权限，让应用发布到能够读取新版本，确认连接池全部切换后，再撤销旧凭证。若数据库只支持单密码，就需要缩短发布窗口并准备回滚凭证，否则容易在应用滚动发布期间打断旧实例。

JWT 签名密钥轮换依赖 Key ID 和密钥集合。签发方先发布包含新公钥的 JWKS，验证方缓存刷新后开始接受新旧两把公钥；随后签发方改用新私钥签名；等旧 Token 超过最长有效期，再从 JWKS 中移除旧公钥。若没有 `kid`、没有缓存刷新策略或 Token 有效期过长，轮换会变成一次不可控的全站登出或长期兼容。

Webhook 密钥轮换通常需要接收方同时接受新旧签名一段时间。更稳妥的协议会在请求中包含 Key ID、时间戳、签名算法和签名值，接收方验证时间窗口并做重放去重。合作方切换到新密钥后，接收方观察旧 Key 是否仍有请求，超过约定窗口再拒绝旧值。

第三方 API Key 轮换要同时处理配额、来源限制和调用方发布节奏。先创建新 Key，配置与旧 Key 等价或更小的权限，把调用方切过去，监控旧 Key 调用量归零，再禁用旧 Key。若平台支持 IP、域名、应用包名或签名证书绑定，应在轮换时一并收紧，避免把“谁都能用的万能钥匙”复制成两个。

加密密钥轮换要区分重新包装和重新加密。信封加密下，轮换 KEK 通常只需用新 KEK 重新包装 DEK；若 DEK 本身泄漏，才需要重新生成 DEK 并重写受影响数据。签名密钥泄漏要求停止信任旧签名；加密密钥泄漏则可能要求评估历史密文是否已经失密。两者的应急处置不能混用。

## 信封加密解决了什么问题

如果一百万条记录都直接用同一把主密钥加密，轮换主密钥意味着重写一百万条记录；如果为每条记录建立一把由人工管理的密钥，密钥系统本身又会失控。信封加密把这两种责任分开：数据加密密钥（DEK）负责高效加密业务数据，KMS 中的密钥加密密钥（KEK）只负责包装 DEK。

业务系统保存密文、被包装的 DEK、算法与密钥版本。读取时，获得授权的工作负载请求 KMS 解开 DEK，再在内存中完成数据解密。轮换 KEK 时只需重新包装体积很小的 DEK，不必立即重写全部业务数据；不同租户或数据集合还可以使用不同 DEK，把一次泄漏的影响限制在较小范围。

信封加密并不替代授权。一旦应用已经拿到明文，数据库加密无法阻止它把数据返回给错误用户。加密保护的是存储介质、备份和密钥边界，业务服务仍要对每次使用执行对象权限和目的限制。

信封加密的关键是把元数据保存完整。每段密文至少要能找到算法、模式、Nonce 或 IV、认证标签、DEK 包装结果、KEK 标识、密钥版本和上下文。上下文可以绑定租户、表名、字段名或资源 ID，使同一个被包装密钥不能被随意挪到另一类数据上使用。使用 AEAD 算法时，附加认证数据不加密但会参与完整性校验，适合承载这类上下文。

不要重复使用需要唯一性的 Nonce 或 IV。很多对称加密模式的安全性都建立在“同一密钥下 Nonce 不重复”之上，工程实现中应优先使用成熟库和平台接口，而不是自行拼接随机数和计数器。加密失败、验签失败和解密异常也不应把中间值返回给调用方，否则会形成新的侧信道。

密钥层级还可以服务于权限隔离。按租户、区域、数据等级或业务域拆分 DEK，能够控制一次密钥泄漏或误授权的影响面；按环境拆分 KEK，能够防止测试环境解开生产数据；按用途拆分签名密钥和加密密钥，能够避免一把密钥同时承担多个安全语义。密钥越分散，管理成本越高，因此拆分边界应来自威胁模型，而不是来自命名洁癖。

## 权限、审计与职责分离

密钥系统本身是高价值目标。能管理 KMS 策略的人，不应自动拥有解密业务数据的权限；能使用某把密钥解密的人，不应自动能修改密钥策略；能发布应用的人，也不应能读取所有生产秘密。职责分离不是为了让流程变慢，而是为了防止单个账号失陷后直接取得“修改规则、读取秘密、清理证据”的完整链条。

审计日志应覆盖秘密读取、密钥使用、策略修改、版本创建、禁用、销毁、导出尝试和失败访问。日志里不能记录秘密值本身，但要能回答主体、来源、资源、动作、结果、时间和关联请求。高风险事件还应触发检测，例如非工作时间大量解密、某个工作负载读取不属于它的秘密、旧密钥在停用窗口后仍被调用、CI 任务突然请求生产部署凭证。

秘密的访问策略要能表达环境和上下文。开发者本机不应读取生产数据库密码；测试集群不应解开生产密文；同一服务在灰度环境和生产环境的权限也应分开。网络边界可以作为辅助条件，但不能替代身份，因为攻击者拿到内部执行点后，网络位置就会变成它的优势。

## 泄漏后的处置顺序

秘密扫描发现源码中出现密钥时，删除那一行代码远远不够。历史提交、构建产物、缓存、镜像层、工单、日志和聊天记录都可能已经留下副本。处置的第一步通常是撤销或禁用旧值，而不是美化仓库历史。

接下来要判断这份秘密代表的能力是否被使用。API Key 要查调用日志、来源 IP、User-Agent、调用接口、配额异常和下游数据访问；签名私钥要查是否出现异常签名产物和伪造令牌；加密密钥要判断攻击者是否同时获得密文和解密能力；数据库密码要查登录来源、查询范围、导出行为和权限变化。

清理阶段要覆盖所有副本。仓库历史可以重写，但已经拉取到本地的副本无法靠一次提交消失；镜像和构建缓存需要下架或过期；日志中的秘密要脱敏或隔离；第三方平台上的旧 Key 要确认禁用。最后应把事件转化为控制改进，例如提交前扫描、CI 阻断、Secret Manager 引用、短期凭证、最小权限和异常检测。

如果泄漏的是根密钥、证书私钥或用于签发大量下游凭证的密钥，影响评估要沿信任链展开。根密钥泄漏意味着它签发或包装过的子密钥也可能失去可信基础；证书私钥泄漏可能需要吊销证书、更新固定公钥配置和排查中间人风险；JWT 私钥泄漏可能需要批量撤销会话并缩短兼容窗口。

## 算法也有生命周期

很多系统认真轮换密钥，却把算法名称写死在代码里。若密文没有记录算法和版本，将来淘汰旧算法时，系统甚至不知道应用哪种方式解开历史数据。密码学敏捷性的基本做法，是让密文、签名和协议携带受控的算法与密钥版本，使系统能够在迁移期双读或双验；但算法选择必须由可信配置决定，不能让不可信输入要求服务降级到弱算法。

对于需要保密数十年的数据，还要考虑“攻击者今天收集密文，未来用更强计算能力解开”的风险。后量子密码迁移会是长期工程，但正确做法不是自行拼装一个混合算法，而是先清点长期密钥和数据寿命，保证协议可替换，再跟随成熟标准与平台实现迁移。

密码学敏捷性还要求拒绝算法混淆。验证 JWT 时不能因为 Header 写了 `none` 或弱算法就照单全收；验签方应从可信配置中知道某个发行方允许哪些算法、哪些 Key ID 和哪些用途。加密数据也不应由调用方任意指定“请用旧算法解密”，否则迁移兼容期会变成永久降级入口。

长期数据的迁移要可分批、可回滚、可观察。常见做法是新写入使用新算法和新密钥，读取旧数据时识别旧版本并按需重写，后台任务逐步扫描重加密，最后在指标确认旧版本归零后禁用旧算法。这个过程需要记录失败项和重试策略，否则最难处理的少数历史数据会让旧算法被迫保留多年。

## 一份可落地的最小基线

对多数联网系统来说，密钥与秘密管理至少应满足这些约束：源码、镜像、普通配置和日志中不保存长期秘密；生产、测试和开发环境使用不同秘密；每项秘密有所有者、用途、权限范围、版本和撤销步骤；高价值密钥放入 KMS 或 HSM，私钥材料不随意导出；工作负载优先使用短期身份换取凭证；轮换方案经过演练，而不是只写在制度里。

同时，系统要把秘密使用变成可观察事实。谁读取了哪个 Secret，谁调用了哪把 KMS Key，旧版本是否仍被使用，异常来源是否正在批量解密，泄漏扫描发现后是否自动创建处置流程，这些问题都应能通过日志、指标和告警回答。没有可观察性，轮换和撤销就只能靠希望。

秘密之所以危险，不在于字符串被人看见，而在于看见之后仍然能够做什么。好的密钥管理并不是让秘密永远不泄漏，而是在泄漏不可避免时，让它代表的权力更小、寿命更短、使用更可见、撤销更确定。
