下面给你一个**自上而下的安全防护框架**。你可以把 BBM 系统看成一个“摄像头/音视频设备 + 用户端 App + 云端服务 + 直播/分享链路 + 后台管理 + 运维平台”的复合系统。不要先从 TLS、加密、权限这些点状问题入手，而要先从**资产、信任边界、攻击面、控制措施、运营闭环**来拆。

业界上层风险管理可以参考 NIST CSF 2.0 的“治理、识别、保护、检测、响应、恢复”思路；Web/API 安全可参考 OWASP ASVS 和 OWASP API Security，尤其 API 对象级授权是视频、设备、家庭成员、分享链接这类系统的高频风险点；IoT/摄像头侧可参考 NIST IoT 设备基线中对设备身份、配置、数据保护、接口访问、安全更新和安全状态感知的要求。([NIST][1])

---

## 1. 先定义 BBM 系统里到底要保护什么

BBM 系统最核心的资产通常不是“服务器”，而是下面这些：

| 资产                 | 安全风险                     |
| ------------------ | ------------------------ |
| 摄像头实时画面、音频         | 被偷看、截流、录屏、重放、串流、非法转播     |
| 历史录像、截图、事件片段       | 泄露、越权下载、批量爬取、长期留存带来的隐私风险 |
| 用户账号、家庭成员关系、设备绑定关系 | 越权查看他人设备、被恶意邀请、被夺权       |
| 分享链接、直播间、观看凭证      | 链接泄露、权限失控、转发扩散、盗链        |
| 设备本身               | 被劫持、刷恶意固件、弱口令、调试口暴露      |
| 管理后台               | 运维人员越权、客服误操作、内部人员滥用      |
| 云端 API、流媒体服务、消息服务  | 鉴权绕过、重放、资源滥用、DDoS        |
| 密钥、证书、Token、推流地址   | 泄露后造成大规模设备/流媒体被控制        |
| 日志、告警、审计记录         | 泄露隐私，或缺失导致事后无法追责         |

所以 BBM 的安全目标至少包括：**不可被陌生人看、不可被非授权家庭成员看、不可被后台人员随意看、不可被劫持推流、不可被盗链转播、设备不可被恶意控制、数据泄露后影响可控、出问题后能发现和追溯。**

# 一、业务权限与信任边界

这是最容易被忽视、但最关键的一层。很多系统用了 HTTPS、Token、加密，但最后还是因为**权限模型混乱**导致越权。

## 1. 核心问题

BBM 系统里通常有这些主体：

| 主体     | 可能权限                    |
| ------ | ----------------------- |
| 设备拥有者  | 绑定、解绑、配置、邀请成员、看直播、看录像   |
| 家庭成员   | 看直播、看部分录像、接收告警          |
| 临时访客   | 只在指定时间看指定设备/指定直播        |
| 客服     | 查看设备状态、协助排障，但不应直接看画面    |
| 运维/管理员 | 管理系统配置、排查问题，但应最小化访问敏感内容 |
| 设备     | 推流、上报状态、接收配置、拉取升级包      |
| 第三方服务  | 推送、短信、CDN、存储、AI 分析等     |

最常见的安全事故不是“没加密”，而是：

* A 用户能通过修改 `deviceId` 看到 B 用户摄像头。
* 被移除的家庭成员仍能通过旧 Token/旧链接访问直播。
* 分享链接永久有效，被转发后无法控制。
* 客服/运营后台能直接查看用户实时画面。
* 设备解绑后仍可向原账号推流或接受控制。
* 管理员可以越权导出用户隐私数据。
* API 只校验“已登录”，不校验“是否有权访问这个设备/视频/家庭”。

OWASP API Security 2023 把对象级授权问题列为 API 的首要风险之一，原因就是 API 往往暴露对象 ID，必须在每个访问用户对象的接口中做对象级权限校验。([OWASP][2])

## 2. 应建立的权限模型

建议用“资源 — 动作 — 主体 — 条件”的模型：

```text
主体：用户 / 家庭成员 / 访客 / 设备 / 管理员 / 服务账号
资源：设备 / 直播流 / 历史录像 / 截图 / 家庭组 / 分享链接 / 告警事件
动作：查看 / 下载 / 删除 / 配置 / 分享 / 解绑 / 邀请 / 推流 / 管理
条件：时间 / 地域 / 设备状态 / 分享有效期 / 是否二次确认 / 风险等级
```

例如：

| 场景        | 正确控制                    |
| --------- | ----------------------- |
| 查看直播      | 用户必须属于设备所属家庭，且有直播查看权限   |
| 查看录像      | 要区分“实时看”和“历史回放”权限       |
| 分享给访客     | 需要有效期、次数限制、可撤销、不可扩大授权   |
| 解绑设备      | 需要所有者权限，最好加二次验证         |
| 后台查看设备状态  | 可看在线状态、版本、日志摘要，但默认不可看画面 |
| 管理员查看敏感数据 | 需要工单、审批、审计、脱敏、最短时间授权    |

# 二、账号与身份认证安全

## 1. 用户账号风险

常见风险：

* 弱口令、撞库、暴力破解。
* 手机号/邮箱验证码被刷。
* 登录态 Token 被盗。
* 多端登录无法管理。
* 账号注销后数据仍可访问。
* 家庭成员邀请链路被滥用。
* 找回密码流程绕过。
* 社交登录/OpenID 绑定错误。

## 2. 防护建议

| 控制点   | 建议                                                   |
| ----- | ---------------------------------------------------- |
| 登录认证  | 密码 + 短信/邮箱/Passkey/第三方登录按风险选择                        |
| Token | 短期 Access Token + 长期 Refresh Token；Refresh Token 可吊销 |
| 高危操作  | 解绑设备、邀请成员、删除录像、导出数据时二次验证                             |
| 风险控制  | 异地登录、新设备登录、异常 IP、频繁失败触发风控                            |
| 会话管理  | 用户可查看并踢掉已登录设备                                        |
| 验证码   | 防刷、限频、图形/行为验证、短信轰炸防护                                 |
| 账号恢复  | 不要只靠一个弱凭证恢复账号                                        |

# 三、设备身份与绑定安全

BBM 有摄像头，就不能只把它当普通 Web 系统。设备本身是一个重要攻击面。NIST IoT 基线强调 IoT 设备应具备唯一设备识别能力，且设备配置变更应只允许授权实体执行；这类要求非常适合 BBM 摄像头场景。([NIST Publications][3])

## 1. 设备侧常见风险

* 出厂默认密码相同。
* 设备 SN、MAC、二维码可被猜测或复制。
* 绑定码长期有效。
* 设备被他人抢绑。
* 设备恢复出厂后仍残留旧用户数据。
* 本地调试口 UART/JTAG 未关闭。
* 固件中硬编码密钥。
* 设备证书泄露后可伪造设备。
* 设备离线重连后身份校验不严格。
* 局域网发现协议暴露敏感信息。
* OTA 升级包未签名或可降级到漏洞版本。

## 2. 设备绑定流程要重点设计

推荐流程：

```text
设备出厂：写入唯一设备身份 / 证书 / 安全芯片或安全存储
首次开机：用户扫码或近场配网
绑定：云端校验设备身份 + 用户身份 + 一次性绑定凭证
绑定成功：建立 device-owner 关系
后续访问：所有设备操作都基于 device-owner / family ACL 授权
解绑/转让：清除云端绑定关系 + 清除设备本地敏感数据
```

## 3. 关键防护

| 项目     | 要求                            |
| ------ | ----------------------------- |
| 设备唯一身份 | 每台设备唯一证书/密钥，不能全局共用            |
| 安全启动   | 防止刷入未授权固件                     |
| OTA 升级 | 升级包签名校验、防回滚、灰度、失败回滚策略         |
| 本地接口   | 关闭非必要端口、调试口量产关闭或熔断            |
| 配网安全   | 配网凭证短期有效，避免明文传输 Wi-Fi 密码      |
| 设备重置   | 重置后清理 Token、Wi-Fi、用户数据、密钥派生材料 |
| 设备状态   | 上报固件版本、配置状态、安全事件，便于检测异常       |

NIST IoT 基线也把数据保护、接口访问控制、安全更新和安全状态感知作为设备级核心能力，分别对应 BBM 中的设备加密、接口收敛、OTA 和设备异常监控。([NIST Publications][3])

# 四、通信链路安全：不只是 TLS

你提到 TLS，这是必要但远远不够。

## 1. 需要保护的链路

| 链路             | 风险                   |
| -------------- | -------------------- |
| App ↔ 云端 API   | 中间人、Token 泄露、重放、越权   |
| 设备 ↔ 云端控制通道    | 伪设备、伪服务器、命令注入        |
| 设备 ↔ 流媒体服务     | 推流地址泄露、伪造推流、串流       |
| App ↔ 流媒体服务    | 拉流鉴权绕过、盗链            |
| 云服务 ↔ 对象存储/CDN | 存储桶公开、签名 URL 泄露      |
| 内部微服务之间        | 内网裸奔、服务身份伪造          |
| 后台 ↔ 管理 API    | 管理员 Token 被盗、CSRF、越权 |

## 2. TLS 层应检查什么

| 项目   | 建议                            |
| ---- | ----------------------------- |
| 协议版本 | 禁用过旧 TLS 版本，使用现代 TLS 配置       |
| 证书校验 | App/设备必须严格校验证书链和域名            |
| 证书固定 | 高敏场景可考虑证书/公钥 Pinning，但要设计轮换机制 |
| 双向认证 | 设备到云端建议使用 mTLS 或设备证书          |
| 内部服务 | 服务间通信也应认证和加密，不要默认信任内网         |
| 重放防护 | 请求签名、时间戳、nonce、Token 短有效期     |
| 密钥轮换 | 证书、Token、推流密钥要可轮换、可吊销         |

## 3. 常见误区

* “用了 HTTPS 就安全”：不对，HTTPS 只保护传输，不解决权限。
* “内网不用加密”：不对，云环境和容器环境里内网也可能被横向移动。
* “推流地址够复杂就行”：不够，需要鉴权、时效、绑定设备身份。
* “Token 放 App 里没问题”：移动端可被逆向，不能把长期密钥硬编码在客户端。

# 五、摄像头音视频数据防护

这是 BBM 的核心。

## 1. 实时音视频风险

| 风险     | 示例                    |
| ------ | --------------------- |
| 非授权观看  | 用户改 deviceId 看到别人的摄像头 |
| 串流     | A 设备的流被错误分配给 B 用户     |
| 盗链     | 拉流 URL 被复制到外部播放器      |
| 重放     | 旧的播放地址或媒体分片被重复访问      |
| 中间人    | 弱证书校验导致流被截获           |
| 服务端误路由 | 流媒体服务路由表错误导致画面错配      |
| 录屏外泄   | 合法观看者录屏后传播            |
| 元数据泄露  | 封面图、设备名、时间戳泄露家庭隐私     |

## 2. 实时流防护措施

| 层面      | 控制                            |
| ------- | ----------------------------- |
| 推流鉴权    | 设备推流必须绑定设备证书/Token，不接受匿名推流    |
| 拉流鉴权    | 每次播放都校验用户是否有该设备的观看权限          |
| URL 签名  | 拉流地址短有效期、绑定用户/设备/会话/IP 或设备指纹  |
| 流 ID 隔离 | streamId 不可预测，不直接暴露内部设备 ID    |
| 会话控制    | 限制同一分享链接/用户的并发观看数             |
| 防盗链     | Referer 不能作为唯一依据，应使用签名 Token  |
| CDN 控制  | 私有 CDN、鉴权边缘节点、短期签名、禁止公开缓存敏感片段 |
| 日志审计    | 记录谁在何时从何处观看哪个设备               |
| 异常检测    | 同一账号多地同时看、多设备频繁拉流、异常带宽报警      |

## 3. 历史录像防护

历史录像比实时流更容易造成长期泄露。

需要关注：

* 录像是否默认开启？
* 保存多久？
* 是否支持用户删除？
* 删除是逻辑删除还是物理删除？
* 对象存储路径是否可枚举？
* 缩略图、封面图是否单独鉴权？
* AI 事件片段是否包含敏感画面？
* 录像下载是否需要二次验证？
* 管理后台是否能直接下载？
* 备份里的录像是否同步删除？

建议：

```text
录像文件加密存储
对象存储桶默认私有
访问通过短期签名 URL
签名 URL 绑定用户权限
下载/导出独立审计
录像生命周期策略自动清理
删除请求同步清理索引、缓存、转码文件、缩略图、备份策略
```

# 六、分享功能权限

分享功能是 BBM 里最容易“产品体验”和“安全边界”冲突的地方。

## 1. 分享功能风险

* 分享链接永久有效。
* 链接被转发后不可控。
* 被邀请者可以再次邀请别人。
* 访客权限过大，可以看历史录像或配置设备。
* 分享取消后旧播放会话仍然有效。
* 分享链接可被爆破。
* 分享页面泄露设备名、家庭名、地理位置、儿童/老人信息。
* 通过分享链接绕过登录。
* 分享二维码截图后长期可用。

## 2. 分享权限应拆细

| 权限      | 是否建议默认开放      |
| ------- | ------------- |
| 看实时直播   | 可选            |
| 听音频     | 应单独开关         |
| 看历史录像   | 默认不开放         |
| 下载录像    | 默认不开放         |
| 截图      | 只能尽量限制，无法完全防止 |
| 控制摄像头云台 | 默认不开放         |
| 对讲      | 高风险，默认不开放     |
| 邀请其他人   | 默认不开放         |
| 修改设备配置  | 不开放           |

## 3. 分享链接设计

建议：

* 链接有有效期，例如 10 分钟、1 小时、24 小时。
* 可设置观看时间窗口。
* 可限制观看次数或并发数。
* 可随时撤销。
* 撤销后立即吊销播放 Token。
* 分享访问需要最小化信息展示。
* 高敏设备不允许匿名分享，必须登录后访问。
* 分享 Token 不直接等于资源权限，服务端每次仍要查 ACL。
* 分享操作、访问记录、撤销记录全部审计。

# 七、直播防串流、防盗链、防错配

你提到“直播防串流”，这块要单独看，因为它不只是安全问题，也可能是架构路由问题。

## 1. 串流类型

| 类型    | 说明                        |
| ----- | ------------------------- |
| 权限串流  | 用户拿到了不属于自己的播放地址           |
| 路由串流  | 流媒体服务把 A 设备流路由到 B 会话      |
| 缓存串流  | CDN/边缘缓存错误复用媒体片段          |
| ID 串流 | streamId、deviceId 可预测或被枚举 |
| 推流串流  | 攻击者伪造设备向合法 streamId 推流    |
| 运维串流  | 后台调试、转码、录制任务绑定错资源         |
| 分享串流  | 分享 Token 被滥用或扩散           |

## 2. 防串流设计要点

```text
设备身份 ≠ streamId ≠ 用户可见 ID
推流 Token 与设备强绑定
拉流 Token 与用户、设备、会话、权限强绑定
每次播放前服务端做实时授权检查
流媒体服务不要只信任前端传入的 streamId
CDN 缓存 Key 必须包含权限相关隔离信息
录像、转码、截图任务必须校验资源归属
```

## 3. 必须做的测试

* A 用户修改 deviceId / streamId / familyId 是否能看 B 的流。
* A 用户拿到 B 的拉流 URL 是否能播放。
* 分享撤销后，正在播放的会话是否能继续播放。
* 设备解绑后，旧推流 Token 是否还能推流。
* CDN 缓存是否会跨用户复用。
* 多租户情况下，租户 A 是否能访问租户 B 资源。
* 转码/截图/录像任务是否可能错绑设备。

# 八、用户敏感信息与隐私保护

BBM 的隐私敏感度通常很高，因为音视频可能涉及儿童、老人、家庭环境、作息、地理位置。

## 1. 敏感数据分类

| 数据类型    | 示例                     |
| ------- | ---------------------- |
| 账号数据    | 手机号、邮箱、头像、昵称           |
| 家庭关系    | 家庭组、成员身份、邀请记录          |
| 设备数据    | 设备名、房间名、SN、IP、Wi-Fi 信息 |
| 音视频数据   | 实时流、录像、截图、缩略图          |
| 行为数据    | 观看记录、告警事件、登录记录         |
| 位置/网络数据 | IP、地理位置、时区             |
| 生物/人体相关 | 人形检测、人脸、哭声、动作识别        |
| 运维日志    | Token、URL、设备标识、错误堆栈    |

## 2. 数据保护原则

| 原则   | 落地方式                  |
| ---- | --------------------- |
| 最小采集 | 不采不必要数据               |
| 最短保留 | 录像、日志、截图设置生命周期        |
| 默认私有 | 存储桶、CDN、索引默认不公开       |
| 分级加密 | 音视频、Token、密钥、个人信息分级保护 |
| 脱敏展示 | 后台、日志、客服系统默认脱敏        |
| 用户可控 | 用户能关闭录制、删除录像、撤销分享     |
| 可追溯  | 谁看过、谁下载过、谁导出过要有审计     |
| 数据隔离 | 用户、家庭、租户、环境之间强隔离      |

## 3. 特别要注意日志

很多系统真实泄露点不是数据库，而是日志。

不要在日志中记录：

* 完整播放 URL。
* 完整 Token。
* 完整手机号/邮箱。
* 设备 Wi-Fi 密码。
* 明文验证码。
* 对象存储签名 URL。
* 用户音视频截图路径。
* 管理员操作时看到的敏感内容。

# 九、App / 小程序 / Web 前端安全

## 1. 移动端常见风险

* App 被逆向，硬编码密钥泄露。
* 本地缓存录像、截图、Token 未加密。
* Root/Jailbreak 环境下数据被提取。
* WebView 被注入。
* 深链链接被劫持。
* 证书校验被绕过。
* 调试日志泄露播放地址。
* App 使用过期 SDK。
* 小程序参数被篡改导致越权。

## 2. 防护建议

| 项目        | 建议                         |
| --------- | -------------------------- |
| 本地存储      | Token 使用系统安全存储；敏感缓存加密      |
| 密钥管理      | 不在客户端硬编码长期密钥               |
| 网络安全      | 严格证书校验，必要时 Pinning         |
| 反调试/反篡改   | 可做基础加固，但不能依赖它作为唯一安全措施      |
| WebView   | 禁止不必要 JS Bridge，限制域名白名单    |
| Deep Link | 校验来源、参数签名、防止越权跳转           |
| 截图/录屏     | 可做水印、风险提示、部分平台限制，但不能承诺完全防止 |
| 版本治理      | 强制升级高危漏洞版本                 |

# 十、服务端与 API 安全

OWASP ASVS 可作为 Web/API 安全验证基线，它覆盖认证、访问控制、输入处理、错误处理、日志等应用安全控制验证要求。([OWASP][4])

## 1. API 常见问题

* 只认证不授权。
* 对象 ID 可枚举。
* 水平越权：用户访问其他用户设备。
* 垂直越权：普通用户调用管理员接口。
* 批量接口绕过单个资源权限。
* GraphQL/聚合接口暴露过多字段。
* 参数污染、Mass Assignment。
* 文件上传导致恶意文件或覆盖。
* 回调接口未验签。
* 限流缺失导致短信、验证码、AI 分析、转码成本被刷。
* 错误信息暴露内部结构。

## 2. API 防护清单

| 类型    | 防护                         |
| ----- | -------------------------- |
| 鉴权    | 所有 API 默认需要身份，少量公开接口单独标记   |
| 授权    | 每个资源访问都查主体是否有权             |
| 对象 ID | 使用不可预测 ID，但不能用它替代权限校验      |
| 输入校验  | 白名单校验、类型校验、长度限制            |
| 输出控制  | 不返回多余字段，敏感字段脱敏             |
| 幂等与重放 | 高危操作用 nonce、时间戳、幂等键        |
| 限流    | 用户、IP、设备、接口、租户多维限流         |
| 审计    | 登录、分享、观看、下载、解绑、后台操作必须记     |
| 错误处理  | 不暴露堆栈、SQL、内部服务地址           |
| 安全测试  | 越权测试、模糊测试、接口契约测试、DAST/SAST |

---

# 十一、后台管理系统安全

后台是高危系统。很多 BBM 系统真正的灾难来自后台权限过大。

## 1. 后台风险

* 管理员弱口令。
* 没有 MFA。
* 权限分配粗糙，客服也能看画面。
* 超级管理员账号共享。
* 管理员可批量导出用户数据。
* 无审批、无工单、无审计。
* 后台接口可被普通用户 Token 调用。
* 测试后台暴露公网。
* 内部人员滥用权限偷窥用户画面。
* 日志无法证明谁看过什么。

## 2. 后台权限设计

后台权限应按“职责”拆分，而不是一个 admin 走天下：

| 角色      | 权限                    |
| ------- | --------------------- |
| 客服      | 查账号状态、设备在线状态、工单，不看音视频 |
| 二线技术支持  | 查看脱敏日志、设备诊断信息         |
| 安全运营    | 查看风险事件、封禁、审计          |
| 运维      | 管理服务配置，不直接访问用户内容      |
| 内容/合规审核 | 仅在合法合规流程下访问特定内容       |
| 超级管理员   | 极少数，必须 MFA、审批、全量审计    |

## 3. 后台敏感操作控制

高危动作必须：

```text
MFA
工单号
审批
最小时间授权
操作理由
操作前后快照
全量审计
异常告警
定期复核
```

尤其是“查看用户实时画面/录像”这类能力，默认应该没有。确实需要时，应走临时授权和用户同意或合规流程。

# 十二、云基础设施与运维安全

## 1. 云上风险

* 对象存储桶公开。
* CDN 缓存策略错误。
* K8s API 暴露。
* 数据库公网开放。
* Redis/Elasticsearch 未鉴权。
* IAM 权限过大。
* CI/CD 密钥泄露。
* 测试环境连接生产数据。
* 备份未加密。
* 镜像存在漏洞。
* 运维跳板机无审计。
* 安全组过宽。
* 日志平台泄露敏感数据。

## 2. 防护建议

| 层面   | 建议                                 |
| ---- | ---------------------------------- |
| 网络   | 生产环境分区，数据库不暴露公网                    |
| IAM  | 最小权限，服务账号分离，定期轮换                   |
| 密钥   | KMS/Secret Manager 管理，不写入代码和镜像     |
| 存储   | 默认私有、加密、生命周期、访问日志                  |
| 容器   | 镜像扫描、非 root、只读文件系统、限制能力            |
| K8s  | RBAC、NetworkPolicy、API Server 访问限制 |
| 数据库  | 加密、备份、审计、最小账号权限                    |
| CDN  | 私有分发、签名 URL、缓存隔离                   |
| 运维   | 堡垒机、MFA、命令审计、临时授权                  |
| 环境隔离 | dev/staging/prod 账号、网络、数据隔离        |

# 十三、供应链与研发安全

BBM 依赖很多第三方：摄像头芯片 SDK、P2P/RTC SDK、云存储、CDN、推送、AI 模型、App SDK、开源库。供应链风险不能忽略。

## 风险点

* 第三方 SDK 采集过多数据。
* SDK 存在远程代码执行漏洞。
* NPM/PyPI/Maven 依赖投毒。
* 固件构建环境被污染。
* CI/CD 泄露签名证书。
* 镜像仓库被替换。
* OTA 包被篡改。
* 开发人员误提交密钥。
* 外包代码存在后门。

## 防护

* SBOM：记录软件组件清单。
* 依赖漏洞扫描。
* 代码签名、固件签名、镜像签名。
* CI/CD 最小权限。
* 构建产物可追溯。
* Secret 扫描。
* 第三方 SDK 安全评估。
* 发布前安全门禁。
* 高危漏洞快速修复机制。

NIST SSDF 的目标就是把安全软件开发实践嵌入软件生命周期，包括准备组织、保护软件、生产安全良好的软件、响应漏洞等方向。([NIST Publications][5])

# 十四、安全监控、审计与应急

安全不是上线前做完就结束。BBM 需要持续监控。

## 1. 必须监控的行为

| 行为   | 异常示例                   |
| ---- | ---------------------- |
| 登录   | 异地、新设备、失败暴增            |
| 设备绑定 | 大量绑定失败、同一账号绑定异常多设备     |
| 观看直播 | 同账号多地观看、陌生 IP 访问       |
| 分享   | 大量创建分享链接、链接访问来源异常      |
| 拉流   | 带宽突增、Token 重放、CDN 命中异常 |
| 录像下载 | 批量下载、后台导出              |
| 后台操作 | 管理员访问敏感资源、越权尝试         |
| 设备状态 | 固件异常、频繁重启、异常推流         |
| API  | 频繁 403/404、枚举 ID、限流触发  |
| 存储   | 对象访问突增、公开策略变更          |

## 2. 审计要求

审计记录至少包括：

```text
谁
在什么时间
从哪里
用什么客户端/设备
访问了哪个资源
做了什么动作
是否成功
请求关联 ID
授权依据
风险评分
```

特别是：

* 谁看过哪个摄像头。
* 谁分享了链接。
* 谁撤销了分享。
* 谁下载了录像。
* 谁在后台查看了用户资料。
* 谁修改了设备配置。
* 谁解绑/重置了设备。

## 3. 应急预案

要提前准备：

* Token/证书批量吊销。
* 单个设备封禁。
* 单个用户冻结。
* 分享链接全量失效。
* 某版本 App/固件强制升级。
* 某区域 CDN 下线。
* 存储桶误公开后的排查脚本。
* 日志取证流程。
* 用户通知模板。
* 监管/合规通报流程。

# 十五、合规与隐私设计

BBM 如果涉及家庭、儿童、老人、室内视频，隐私风险会非常高。

需要考虑：

* 用户同意与告知。
* 摄像头开启状态提示。
* 音频采集提示。
* 录像保存周期。
* 用户删除权。
* 数据导出权。
* 账号注销后的数据清理。
* 儿童相关数据的特殊保护。
* 跨境传输。
* 第三方 SDK 数据共享。
* 后台人员访问用户内容的合法性。
* 安全事件通知机制。

隐私不是写一份隐私政策就结束，而是要落实到产品能力里：**能关、能删、能查、能撤销、能审计、能最小化。**

# 十六、可以落地成一张 BBM 安全全景表

| 层级     | 重点问题           | 核心控制                    |
| ------ | -------------- | ----------------------- |
| 业务权限   | 谁能看哪个设备/录像/分享  | RBAC + ABAC + 对象级授权     |
| 账号安全   | 撞库、盗号、Token 泄露 | MFA、风控、会话管理、Token 吊销    |
| 设备安全   | 假设备、抢绑、恶意固件    | 设备证书、安全启动、OTA 签名、防回滚    |
| 传输安全   | 中间人、重放、伪服务端    | TLS/mTLS、签名、nonce、证书校验  |
| 音视频安全  | 偷看、盗链、串流       | 推拉流鉴权、短期 URL、流隔离、审计     |
| 分享安全   | 链接扩散、权限过大      | 有效期、可撤销、最小权限、访问记录       |
| 数据安全   | 录像泄露、日志泄露      | 加密存储、私有桶、脱敏、生命周期        |
| API 安全 | 越权、注入、枚举       | 统一鉴权授权、输入校验、限流          |
| 后台安全   | 内部滥用、误操作       | MFA、审批、最小权限、全审计         |
| 云安全    | 存储公开、密钥泄露      | IAM、KMS、网络隔离、配置扫描       |
| 研发安全   | 依赖漏洞、CI/CD 泄露  | SAST、SCA、Secret 扫描、签名发布 |
| 运营安全   | 发现不了、追不了       | SIEM、告警、审计、应急预案         |

# 十七、优先级建议

如果资源有限，我建议按这个顺序做：

**P0：必须马上保证**

1. 所有设备、直播、录像、分享接口做对象级授权。
2. 推流和拉流都必须鉴权，不能裸 URL 长期有效。
3. 对象存储、CDN、录像文件默认私有。
4. 后台不能默认查看用户音视频。
5. 设备绑定、解绑、分享、下载录像有完整审计。
6. 用户 Token、设备 Token、分享 Token 可吊销。
7. 后台管理员强制 MFA。
8. 设备 OTA 包签名校验。
9. 日志中不能出现完整 Token、播放 URL、验证码、密钥。
10. 分享链接必须有有效期、可撤销。

**P1：中期完善**

1. 设备证书/mTLS。
2. 播放 URL 绑定用户、设备、会话、短有效期。
3. 异常观看、异常分享、异常拉流检测。
4. App 本地敏感数据加密。
5. CI/CD Secret 扫描和依赖漏洞扫描。
6. 数据生命周期和用户删除机制。
7. 后台工单审批和临时授权。
8. 安全测试自动化：越权测试、接口模糊测试、权限矩阵测试。

**P2：长期治理**

1. 零信任服务间访问。
2. 完整数据分级分类。
3. 隐私影响评估。
4. 红队演练。
5. 供应链安全体系。
6. 安全基线合规检查。
7. 安全事件响应演练。
8. 多区域容灾与恢复演练。

## 最后给你一个判断标准

BBM 安全不要问“有没有 TLS、有没有加密”，而要问这 10 个问题：

1. 一个用户是否有任何办法看到不属于自己的摄像头？
2. 一个家庭成员被移除后，是否所有旧权限立即失效？
3. 一个分享链接被转发后，是否还能控制影响范围？
4. 一个设备被解绑后，是否还能推流或接受控制？
5. 一个管理员是否能在无审批情况下查看用户画面？
6. 一个播放 URL 泄露后，是否很快失效且不能扩大权限？
7. 一个对象存储路径泄露后，是否仍无法直接访问？
8. 一次安全事故后，是否知道谁看了什么、下载了什么、分享了什么？
9. 一个固件包被篡改后，设备是否会拒绝安装？
10. 一个密钥或 Token 泄露后，是否能快速吊销和轮换？

如果这 10 个问题都能回答清楚，BBM 系统的安全架构基本就从“零散防护”进入“体系化防护”了。
