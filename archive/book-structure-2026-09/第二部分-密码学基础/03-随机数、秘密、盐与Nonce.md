# 第 3 章　随机数、秘密、盐与 Nonce：它们为什么出现

假设你正在开发一个普通的账号系统。用户忘记密码时，网站向他的邮箱发送一条重置链接。用户打开链接，设置新密码。系统把新密码保存起来。此后，用户登录并上传一份需要加密保存的文件。

这一小段流程里，系统至少要生成三种看似相似的值：重置链接中的随机 Token、保存密码时使用的盐、加密文件时使用的 Nonce。它们都可能是一串字节，却不是同一种东西。若一开始只背定义，三者很容易混在一起。本章会跟着这条流程，先看一个设计会怎样失败，再看为避免这个失败需要什么性质，最后才给这个性质起名字。读完后，你应该能在看到“这里生成一个随机字符串”时追问：它究竟要防猜测、防重复，还是必须作为秘密保管？

## 3.1　第一道问题：别人能不能猜中重置链接

用户在“忘记密码”页面填写邮箱。网站收到请求时，还不知道发起请求的人是不是账号主人，因此不能立即允许他改密码。它把一个链接发到账号登记的邮箱，并要求访问者拿着链接回来。这里真正授予改密能力的，不是邮箱地址，也不是“请求成功”的提示，而是链接里的那段 Token。系统暂时把“谁能拿到这个值”当作“谁能继续完成这次重置”的依据。

先别急着生成 Token。假如链接只有 `/reset?user=42`，任何知道账号编号的人都能访问。改成 `/reset?user=42&time=...` 也不够：请求时间大致可以猜到。这里的关键不是链接长得复杂，而是攻击者**无法构造另一个人的有效链接**。只有当链接包含一个攻击者不知道、又不能从公开信息推出来的值时，这个方案才开始成立。

现在站在攻击者一侧想一想。他可以知道某人的邮箱，甚至可以为自己的账号申请重置链接，观察自己拿到的 Token。如果 Token 是“用户编号＋当前时间”或一个递增序号，他就能推测别人的值。即使系统再把这些信息做一次 SHA-256，生成的字符串看起来很长，候选输入仍然只有那一小批。这里暂时把 SHA-256 理解成一种“同样输入总得到同样结果”的转换即可，下一章再细讲哈希。攻击者把可能的用户编号和时间逐一计算，便能得到同样的长字符串。编码或哈希只改变外观，不能凭空创造猜不到的信息。

所以，重置 Token 的第一个要求是**不可预测**：看到生成方法和以前发出的值，也不能轻易猜出下一个有效值。它还要足够长，让攻击者即使不断尝试，也难以在有效期内碰中。六位数字验证码只有一百万种可能；一串真正随机生成的长 Token 的候选空间可以大得多。这里说的“熵”，可以先朴素地理解为攻击者面对多少种真正可能、且难以排除的结果。字符数不是熵：固定前缀再加六位随机数字，安全性仍主要来自那六位数字。

可以用一个不涉及复杂公式的例子体会差别。若六位数字的每个组合都等可能，攻击者试一次，大约是在一百万个候选中碰一个；若服务端允许他针对同一操作试很多次，机会便不断累积。把数字码前面加上 `reset-2026-`，只会让链接更长，不会增加候选数。相反，由安全随机接口生成十六个字节，会形成远大得多的候选空间；再把字节写成三十二个十六进制字符，只是换了表示法。判断强度时应回到**真正随机的来源和可尝试的次数**，不要数界面上出现了多少字符。

这并不表示短验证码一概不能用。短码可以通过短有效期、绑定账号与具体操作、严格限制尝试次数等方式控制在线猜测机会。但它不能被当作可长期、无限次尝试的秘密。选择机制时，先问攻击者能够试多少次、每次试错会不会被看见，再决定需要什么样的值。[OWASP 忘记密码指南](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)要求重置 Token 使用安全随机生成方式、足够长、单次使用并在适当时间后失效。

到这里，我们只得到一个需求：“给我一段攻击者难以预测的字节。”机器究竟怎样提供它？

## 3.2　第二道问题：机器怎样产生猜不到的值

计算机执行程序大多遵循确定的规则。若给普通伪随机数生成器相同的初始状态，它会再次输出相同的序列。这对模拟、游戏或测试很方便，却可能让重置 Token 被预测。当前时间、进程号、用户 ID、普通随机函数的输出，即使混合在一起，也不能自动成为安全的种子。

“伪随机”本身并不是贬义词。程序不必每次都直接从物理世界取得一整串随机字节；关键在于，生成器的内部状态如何建立和保护，以及观察者能否根据已知输出推算未来输出。普通随机接口通常只承诺结果在统计上看起来分散，不承诺抵抗主动猜测。安全用途需要更强的承诺，这才引出了密码学安全随机数生成器。

操作系统和成熟密码库提供**密码学安全随机数生成器**。它们使用受控的熵源建立内部状态，再用经过分析的算法持续产生输出。生成过程在内部可以是确定性的；安全目标是外部观察者即使见过许多输出，也无法在合理攻击条件下预测接下来的值。初始熵与生成算法共同重要，[NIST 的随机位生成指南](https://csrc.nist.gov/pubs/sp/800/90/a/r1/final)和[熵源指南](https://csrc.nist.gov/pubs/sp/800/90/b/final)分别讨论这两部分。

开发者不需要自己发明这些算法。调用语言或平台明确标为“适用于密码学用途”的随机接口，让库产生原始字节，再按链接需要编码为十六进制或 URL 安全的 Base64。编码只负责传输：同样的随机字节转成更长的十六进制文本，熵并未增加。不要因为某个 API 名字里有 random，就假定它可用于生成密钥、会话标识或重置 Token；也不要在安全接口失败时悄悄退回普通随机函数。

这一步还能解释一个常见的混淆：**安全随机数是生成方法，不是生成值的身份。**同一接口可以生成会话标识，也可以生成加密密钥；前者要作为可撤销的访问凭证管理，后者要遵循密钥的用途、存储和轮换要求。生成器只负责提供难以预测的字节，不会替应用决定谁能使用它、能用几次、何时失效。

**不可预测**与**不重复**也要分开。数据库的自增主键通常不会重复，却一眼能猜出下一个值；它适合定位记录，不适合直接充当重置 Token。安全随机值通常难以预测，但大量生成时仍需考虑碰撞概率。对必须唯一的记录，数据库唯一约束和冲突处理仍有价值。若值被用在有严格“不重复”要求的密码算法中，范围还必须写清楚：是某个进程内，还是同一把密钥在所有进程中的全部使用记录？

## 3.3　第三道问题：生成之后，Token 怎样一直保持安全

假设我们改用安全随机接口，重置链接已经不能被轻易猜中。若 Web 服务器把完整链接写进访问日志，日志的读者照样可以在链接失效前替用户改密码。生成正确，只解决了“猜测”这一条攻击路径；拿到原值的人仍能使用它。

这类泄漏不只发生在数据库里。完整 URL 可能进入浏览器历史、错误报告、代理日志，或被复制给客服。若重置页面还加载外部资源，也要留意相关浏览器行为和链接传播路径。逐项排查的理由很直接：攻击者不必打败随机数生成器，只要从某处拿到仍然有效的原值，就可以绕过前面的全部猜测难度。

这使 Token 成为一种**秘密**，更准确地说，是一种“仅凭持有就能行使特定能力”的值。它与普通用户 ID 的区别不在格式，而在后果：别人知道用户 ID 不应自动获得改密权，别人拿到有效重置 Token 却可能获得。会话标识、API Key、恢复码也有类似特征。把秘密当作普通字符串在 URL、日志、错误报告、聊天记录和监控标签之间复制，会让最初的防猜测设计失去意义。

因此，一次重置流程至少要规定：Token 属于哪个账号、只允许哪种操作、何时过期、使用一次后如何作废、用户再次申请时旧值怎样处理，以及泄漏后如何撤销。服务端可以只存高熵 Token 的哈希或指纹，收到用户提交的原值后再比对；这样仅泄漏存储记录时，攻击者不一定直接拿到可使用的原值。但这不能补救本来就只有几位数字的短码，因为攻击者可以离线枚举所有候选值。它也不能补救原值已经进入日志的问题。

把它想成一张临时通行证会更容易理解。通行证上写明“只用于给账号甲改密码”，过期时间一到就失效，用过也立刻失效；服务器验证时不仅要比对值，还要检查这些条件。若两个请求几乎同时提交同一 Token，“单次使用”还需要在服务端以可靠的状态变更落实，不能只在页面上隐藏按钮。秘密的安全既取决于能否猜中，也取决于**拿到之后到底能做什么、能做多久**。

邮件把链接送到登记邮箱，只表明有人能够访问那个收件渠道；它本身不证明现实中的身份，也不保证邮箱没有失陷。重置完成后，系统仍要按风险处理现存会话、通知用户，并监控异常。由此可见，“秘密”不是一种特定的密码算法，而是从值所授予的能力推出来的管理要求。

## 3.4　密码不是 Token：为什么又需要盐

用户拿着重置链接设置了新密码。系统接下来面对一个完全不同的难题：密码通常由人选择，容易重复，也不像重置 Token 那样每次都由系统生成。我们不能要求数据库保存明文密码，因为一旦数据库泄漏，攻击者会直接得到所有密码。系统通常保存专用密码哈希算法产生的验证记录：它能用来检查下一次输入是否正确，却不能像解密文件那样直接取回原密码。登录时，再把用户提交的密码按相同规则验证。

这里为什么不能照搬 Token 的办法，让系统给每个人发一段高熵随机值？其实这正是某些密钥或恢复码可以采用的方式，但日常登录密码需要人记住或通过密码管理器使用，现实中会出现短密码、常见词和跨站重复。系统不能把“用户一定会选强密码”作为数据库安全的前提。接下来要解决的，是**低熵、可能相同的用户输入如何保存供日后验证**。

先设想一个过于简单的方案：所有用户都保存同一个快速哈希函数对密码的结果。甲和乙都使用同一个密码，数据库里便出现相同的结果。攻击者可以看出哪些账号密码相同，还可以提前计算常见密码的哈希，与整库记录反复比较。即使看不到明文，攻击也能被规模化。

为了打破这种“同一输入总对应同一存储结果”的关系，系统为**每一次密码存储**生成一个独立的**盐**，把它交给专用密码哈希算法。甲和乙即使输入相同密码，因为盐不同，存储记录也不同。攻击者不能再只计算一次候选密码，就同时匹配整库。这个概念出现的原因，是密码本身缺乏足够多样性、而验证数据库又可能泄漏；它与重置 Token 的“防止外人猜中正在使用的随机值”不是同一个问题。[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)明确要求每条密码使用独立盐。

可以把一次注册和一次登录拆开看。注册时，密码哈希库为这条记录生成专用的盐，用密码和盐运行算法，再存下盐、算法参数和结果；它不保存可直接取回的原密码。登录时，系统把本次输入交给库的验证接口，由它根据记录中的盐和参数判断是否匹配。两个人用了同一密码，因为各自的盐不同，记录仍不同。用户改密码时则产生新的验证记录和新的盐；不要把盐当成全站配置常量。成熟库通常会自动生成和管理盐，应用开发者应优先使用库的标准接口。

盐通常与验证结果放在一起，**不需要保密**。验证时服务端必须取回同一个盐才能检查密码。攻击者看到了盐，仍需要针对各条记录分别猜测。盐也不是“把弱密码变强”的魔法：如果密码是“123456”，而系统仅计算速度很快的 SHA-256，攻击者依然可以逐个账号高速试错。所以实际存储要使用成熟的、刻意提高猜测成本的密码哈希方案及其库，并根据当前平台调整参数。盐和专用密码哈希各有作用，缺一不可。

这也解释了为什么不能把“给密码加盐后算 SHA-256”视作完整方案。盐阻止攻击者把一次计算结果廉价地套用到大量账号；专用密码哈希则提高**每一次猜测**的成本。两者解决的是不同维度的问题。密码存储算法还应能调整工作量，随着设备和攻击能力变化逐步更新；新系统一般应依照当前权威指南选择成熟方案，例如 Argon2id，而不是自己拼接多轮哈希。

有时还会听到 Pepper。它通常是与密码数据库分开管理的共享秘密，可增加数据库单独泄漏后的攻击成本。它不是“更高级的盐”：盐每条记录独立且可公开，Pepper 则需要保密、授权和轮换。初学者先理解盐为什么出现，以及它不能代替专用密码哈希，已经足以避免最常见的设计误区。

## 3.5　密钥已经保密，为什么加密还要 Nonce

用户上传两份文件，系统准备用同一把密钥分别加密。先把密钥理解为只有系统和获授权者掌握的秘密：没有它，旁人不应能还原文件。但“旁人不知道密钥”还不够。我们还得看**算法在重复使用这把密钥时会发生什么**。

先看一台**玩具加密机**，只为理解原因，真实 AES-GCM 并不是这样计算的。它同时接收秘密密钥 K 和本次编号 Nonce。假设输入“K、编号 1”时，机器内部得到数字 4；它把明文数字加 4，得到密文数字。外人即使知道编号 1，只要不知道 K，就不能直接算出这个 4。

文件 A 的某一位明文是 **3**，加密后是 **7**。攻击者碰巧知道 A 原本这一位是 3，又看到了密文 7，于是推知这一次用的数字是 **4**。现在文件 B 的对应位置，攻击者只看到密文 **9**。如果 B 也用了“K、编号 1”，机器会再次得到同一个 4，攻击者就知道 B 原来是 **5**，因为 5 加 4 等于 9。**密钥 K 从未泄漏，但重复使用本次的加密材料，仍然泄露了 B 的内容。**

如果 B 使用“K、编号 2”，机器会产生另一份加密材料；从 A 推出的“4”便不能直接用于 B。这就是 Nonce 在这里的任务：让同一把密钥用于多次加密时，每次得到不同的内部材料。在真实的 AES-GCM 中，加密处理的是字节而非一位数字，Nonce 重复的后果也不止于此，还会严重损害完整性保护。[RFC 5116 关于 AES-GCM 的说明](https://www.rfc-editor.org/rfc/rfc5116.html)明确记录了这种风险。

Nonce 因此不是“再加一把秘密钥匙”，而是交给算法的**本次加密标识**。在这里讨论的方案中，同一把密钥的不同加密操作必须使用不同 Nonce；换了密钥，要求的范围也随之重新计算。Nonce 通常可以和密文放在一起，让解密方取得它。别人看见 Nonce 不等于能解密，因为真正要保密的是密钥；但“可以公开”绝不等于“可以重复”。

Nonce 也不一定要随机。若所用算法允许，可以用受控计数器产生不同值：1、2、3……关键是**同一把密钥下不重复**。如果两台服务器共用密钥却都从 1 开始，或者系统回滚后重复以前的编号，仍然会出错。因此实际做法必须遵循所选算法和密码库对 Nonce 长度、生成方法及使用次数的要求；不要自己随手写一个固定值。并非所有加密方案都按这里的规则工作，本节用 AES-GCM 说明的是一种常见且必须严守的约束。

回看本章前面的概念，区别就清楚了：重置 Token 要让外人**猜不到**，因为拿到原值就可能改密；密码存储的盐要让记录**各不相同**，它可以公开；这里的 Nonce 要保证**同一密钥下每次加密不重复**，它通常也可以公开。判断一个值是否安全，先问它在机制里承担什么任务，而不是看它是不是一串“随机字符”。

## 3.6　同一个名字，为什么登录挑战里也有 Nonce

回到登录这一步，有些认证协议里也会出现 Nonce。服务器发起一次挑战，认证器围绕这次挑战作出响应。服务器只接受与当前交互对应的结果，使攻击者不能把过去记录的一条有效响应直接拿来再次登录。这里的核心是**新鲜性和绑定**：响应属于哪一次登录、哪一个网站、哪一个主体，验证者必须能够判断。

它和文件加密里的 Nonce 同名，是因为两者都要避免把过去的一次操作当成现在的一次操作；但各自的具体要求来自不同协议。登录挑战可能需要攻击者无法提前预测，并有使用期限；某些加密模式的 Nonce 则主要要求在同一密钥下不重复。不能听到“Nonce”就立刻套用固定的长度或随机性规则。先问它在哪个协议里、要阻止什么重放或重复、唯一性的范围是什么。

到这里，一条贯穿本章的线索已经完整：系统发出重置链接时，需要外人猜不到的临时秘密；系统保存人选的密码时，需要每条记录不同的公开盐；系统重复使用加密密钥时，需要按算法规则管理每次操作的 Nonce；认证协议也会使用一次性挑战保证当前响应不能由旧响应冒充。这些概念不是从术语表里凭空出现的，而是为不同的失败方式分别补上的约束。

把账号系统从头走一遍，可以用四个问题检查自己是否真的理解了本章。

| 场景中的值 | 它出现前有什么问题 | 首要要求 | 原值要保密吗 |
| --- | --- | --- | --- |
| 重置 Token | 别人可能伪造改密链接 | 难以预测，并限制用途、期限和次数 | 要。拿到有效原值可能就能改密 |
| 密码存储的盐 | 同密码会形成同结果，猜测可在整库复用 | 每条记录独立，配合专用密码哈希 | 不需要 |
| 文件加密的 Nonce | 同一密钥会反复加密 | 遵守所选算法的规则；本章所述方案要求同密钥下不重复 | 通常不需要 |

第一，重置链接为什么不能用用户 ID 和时间戳生成？因为攻击者能推测候选值；做哈希也不会增加原始熵。它应来自安全随机接口，并受到有效期、单次使用和尝试限制。

第二，重置 Token 已经足够随机，为什么仍不能写入日志？因为它授予改密能力，泄漏原值会绕过“猜测困难”这道防线。秘密的保护必须覆盖整个生命周期。

第三，密码已经做了哈希，为什么还要盐？因为人的密码可能相同且可猜，独立盐能避免同密码同结果和通用预计算；但盐不能替代专用密码哈希算法。

第四，文件加密的密钥足够强，为什么还要 Nonce？因为同一把密钥会重复使用，而很多加密机制要求每次操作拥有符合规定、特别是同一密钥下不重复的输入。密钥强度无法弥补 Nonce 管理错误。

当你在别处看到“生成随机字符串”这样的要求时，不妨先暂停：这个值要防猜、要唯一、要保密，还是要证明一次交互的新鲜性？它的有效范围是一次请求、一个用户、一把密钥，还是所有实例？只有先答出这些问题，才能判断生成器、存储方式和测试是否合适。

## 练习

1. 系统用“用户 ID＋当前分钟”生成重置 Token，再做 SHA-256。它为什么仍可能被猜到？加长哈希输出能否解决？
2. 两名用户设置了同样的密码，数据库中的密码验证记录不同。这说明系统一定安全了吗？盐解决了什么、没有解决什么？
3. 两台服务器共用一把加密密钥，各自用从零开始的计数器作为 Nonce。为什么单台服务器上的“不重复”不足以证明安全？
4. 某人说：“密钥从未泄漏，重复使用同一个 Nonce 也没关系。”这句话忽略了什么？
5. 重置 Token 由安全随机接口生成，但完整链接进入访问日志。应优先排查生成器，还是排查 Token 的分发与失效流程？

### 参考答案

1. 用户 ID 与时间窗口通常可被推测，攻击者可以枚举候选后重复计算同一哈希。改变输出长度不能增加输入的不确定性。
2. 不能。独立盐使相同密码形成不同记录并抑制通用预计算，但弱密码仍可能被逐条猜测，还需要专用密码哈希算法、适当参数和登录保护。
3. 不重复的范围是同一把密钥的全部相关加密调用。两台服务器使用相同计数值时，仍会在这个范围内重复。
4. 它忽略了算法还依赖 Nonce 的使用规则。以 AES-GCM 为例，同一密钥和 Nonce 的组合重复用于不同加密，会重复内部加密材料，可能泄露明文之间的关系，并损害完整性；攻击者不必知道密钥。
5. 优先排查泄漏与使用路径：限制日志访问和记录内容，撤销可能受影响的 Token，检查有效期、单次使用和其他传播渠道。生成器正确不能弥补原值外泄。
