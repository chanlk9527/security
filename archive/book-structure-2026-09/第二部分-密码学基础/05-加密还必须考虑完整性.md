# 第 5 章　加密还必须考虑完整性：看不懂不等于改不了

假设应用把一份配置文件加密后放进普通存储。存储管理员看见的只是一串密文，无法直接读出内容。于是我们是否可以断定：下次解密出来的一定还是原来那份配置？

不能。**保密性**回答“没有密钥的人能否读懂内容”，**完整性**回答“内容是否被改动”。这是两个不同问题。某些加密方式只隐藏内容，却不会可靠地发现密文被删除、替换或修改。攻击者可能不知道原文，却仍能破坏它；在一些可修改的加密方式中，他甚至可能让解密结果发生可预测的变化。

本章从这个缺口出发，逐步说明为什么现代应用通常需要认证加密、认证标签有什么用、哪些公开信息也必须与密文绑定，以及验证失败时为什么不能继续处理数据。读完后，你应能判断一套加密设计到底保护了什么，而不是只看它是否使用了 AES。

## 5.1　第一道问题：密文被改了，谁会知道

先看最简单的破坏。攻击者无法解密文件，但可以把密文中的一个字节改掉。应用稍后使用正确密钥解密，可能得到乱码，也可能只损坏原文的一部分。如果应用没有验证机制，它只能把得到的结果继续交给图片解析器、配置加载器或业务代码，希望“格式不对时自然报错”。

格式报错不能代替安全验证。某些修改可能仍生成格式合法的数据；不同错误还可能向攻击者泄露解密过程的信息。即使攻击者无法控制解密后的精确内容，只要能使关键文件损坏，他也已经破坏了数据可用性。如果系统静默接受了被改变的值，后果会更严重。

再看“整个替换”。系统用同一把密钥加密了两份配置，一份属于普通功能，另一份属于更高权限的功能。攻击者不需要理解任何一份内容，只要把两条存储记录调换。如果加密结果没有和自己的使用位置绑定，应用可能成功解密，并把一份真实但放错位置的数据当成当前记录。这说明完整性不仅是“某个字节有没有变”，还包括**这份数据是否仍属于原来的上下文**。

因此，应用需要在使用明文之前得到一个明确结论：密文及相关上下文与加密时一致，或者验证失败。仅仅“使用了密钥”并不能自动给出这个结论，它取决于采用的加密方案。

## 5.2　认证加密为什么出现

早期系统可能分别选择一种加密算法保护保密性，再选择一种 MAC 保护完整性。理论上可以安全组合，实际却很容易在先后顺序、密钥复用、字段范围和错误处理上出错。现代应用更适合直接使用经过审查的**认证加密**接口，把两种保证作为一个整体获得。

常见名称 **AEAD** 是“带附加数据的认证加密”的英文缩写。它的加密操作可以先抽象成：

~~~text
输入：密钥、Nonce、明文、附加认证数据
输出：密文、认证标签
~~~

相应的解密操作是：

~~~text
输入：密钥、Nonce、密文、附加认证数据、认证标签
输出：明文，或者 FAIL
~~~

这里最重要的不是记住参数顺序，而是最后一行：认证解密应给应用**完整明文或失败**，不应把一份“可能被篡改的明文”交出来让应用猜测是否可信。[RFC 5116](https://www.rfc-editor.org/rfc/rfc5116.html)就是用“明文或 FAIL”描述认证解密的结果。

AES-GCM 和 ChaCha20-Poly1305 是常见 AEAD 方案。算法名称只是选择的一部分；密钥、Nonce、标签和附加数据都必须按对应接口的规则使用。基础手册不要求读者推导它们的数学结构，但要求读者认识这个完整接口。

## 5.3　认证标签是什么

认证标签常写作 Tag。加密时，算法处理密钥、Nonce、明文以及附加认证数据，并为这次结果产生标签；解密时，它根据收到的全部输入检查标签是否匹配。攻击者不知道密钥，通常就不能在改动密文后再计算出一个能通过验证的新标签。

标签可以和密文一起保存或传输，它本身通常不需要保密。它与第四章中的 MAC 有相似目标：让持有密钥的一方发现消息被改动。区别在于，AEAD 把加密和认证作为一个已经定义好的整体接口，应用不必自己决定“先加密还是先计算 MAC”“两者是否使用同一把密钥”等容易出错的问题。

标签不是普通文件哈希。攻击者改了文件后，可以轻易重新计算普通 SHA-256；他没有 AEAD 密钥，却不能同样生成合法标签。标签也不证明某个现实中的具体用户实施了加密：任何获得该密钥的程序或人员都有生成合法密文与标签的能力。

标签还不能自动防止**重放**。攻击者若把过去的一整套合法 Nonce、密文和标签原样拿回来，密码学验证仍可能成功。系统是否允许旧版本再次使用，需要通过版本号、序列号、时间、状态记录或具体协议处理；需要被保护的这些信息应进入明文或附加认证数据。

## 5.4　有些信息不用隐藏，但必须绑定

一份加密文件通常还有公开元数据，例如文档编号、格式版本、创建者编号和用途。应用需要先看到其中一些字段，才能找到密钥或选择解析方式，因此不能把所有信息都塞进密文。但若攻击者能随意修改这些字段，或者把一份密文搬到另一条记录下，系统可能在错误的上下文中使用正确解密出来的内容。

AEAD 为此提供**附加认证数据**，常写作 AAD。AAD 不会被加密，旁人仍能看见；但它参与认证标签的计算。加密时若把“文档编号 42、用途为配置、格式版本 3”作为 AAD，解密时就必须提供完全相同的字节。攻击者把文档编号改成 43，或把密文放到用途不同的位置，标签验证就会失败。

可以这样理解三类输入：

| 数据 | 是否隐藏 | 是否由认证标签保护 |
| --- | --- | --- |
| 明文 | 是，输出为密文 | 是 |
| AAD | 否，保持可见 | 是 |
| 未纳入 AEAD 的其他字段 | 否 | 否 |

最后一行很重要。把一个对象加密，不会自动保护数据库中与它相邻的所有列，也不会自动绑定文件路径、HTTP 请求头或调用者身份。应用必须明确哪些上下文会影响数据解释，把需要防篡改的部分以无歧义的形式纳入明文或 AAD。[RFC 5116](https://www.rfc-editor.org/rfc/rfc5116.html)把 AAD 定义为需要认证但不需要加密的数据。

AAD 也不是访问控制。即使标签证明“文档编号没有被改”，应用仍要判断当前请求者有没有权读取这份文档。密码学绑定数据，授权规则决定谁可以使用它。

## 5.5　解密失败不是一份特殊的明文

标签验证失败可能有多种原因：密文损坏、Nonce 不对、AAD 不一致、标签被修改、用了错误密钥，或者数据格式已经无法识别。应用得到的共同结论只有一个：**不能信任这份输入**。

因此，不应在验证完成前解析、显示或执行业务明文，也不应在失败后“尝试忽略标签继续解密”。流式处理大文件时尤其要确认所用库的语义：有些底层接口可能逐段产生暂存数据，应用必须等整条消息认证完成后才能提交结果。成熟的高层 AEAD 接口通常更容易满足这一要求。

对外错误信息也不宜详细区分“标签错了”“填充错了”“字段解析到第几个字节”。不同响应、耗时或重试行为可能成为攻击者观察内部状态的渠道。应用内部可以记录足以排查版本、密钥标识和数据来源的信息，但日志不能包含密钥或不必要的明文。

一次失败是否说明有人攻击，需要结合环境判断。磁盘损坏、部署时使用错误密钥、记录与 AAD 对不上都会导致失败。系统应拒绝使用数据并保留可调查证据，而不是把所有失败都静默当成空值，也不应自动用新密钥覆盖原数据。

## 5.6　Nonce 与认证加密是什么关系

第三章已经用玩具例子解释过：在 AES-GCM 等方案中，同一把密钥下重复 Nonce 会重复本应只使用一次的内部材料。认证标签并不能补救这个错误；对 AES-GCM 来说，密钥和 Nonce 重复不仅可能泄露明文关系，还会破坏完整性保证。

所以，一条完整的 AEAD 记录通常至少需要保留：

- 能识别算法和数据格式的信息；
- 能找到正确密钥或密钥版本的信息；
- 按算法要求生成的 Nonce；
- 密文；
- 认证标签；
- 解密时能够重建的 AAD。

这不是要求每个应用自行发明二进制格式。应优先采用成熟库、框架或协议已经定义的封装，避免字段截断、顺序不一致和版本升级失败。尤其不要因为 Nonce 和标签可以公开，就在保存时丢掉它们；解密和验证通常需要完全相同的值。

不同 AEAD 算法对 Nonce 长度、生成方式、单个密钥可处理的数据量和标签都有具体限制。使用 AES-GCM 时要特别保证同一密钥下 Nonce 不重复；使用其他方案也必须阅读该接口的规定，不能把某一个算法的参数机械套用给全部算法。[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)给出了 GCM 的定义与使用要求。

## 5.7　为什么不建议自己拼“加密＋哈希”

一种常见误区是：先用某种方式加密，再对密文计算 SHA-256，把两者放在一起。普通哈希没有密钥，攻击者修改密文后也能重新计算摘要，因此不能提供消息认证。

换成 HMAC 仍然需要回答很多问题：加密和认证是否使用不同密钥，HMAC 覆盖密文还是明文，Nonce、算法版本和上下文是否也被覆盖，先验证还是先解密，失败时暴露什么信息。密码学协议可以回答这些问题，但应用开发者没有必要重新设计一遍。

因此，新设计通常应直接选用平台提供的 AEAD 高层接口，并遵守其完整的数据格式和限制。[OWASP 加密存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)也建议优先使用经过认证的加密模式。已有系统若采用分离的加密与 MAC，是否安全要根据确切构造审查，不能仅凭“两个算法都很强”下结论。

## 5.8　加密保护到哪里为止

即使 AEAD 使用完全正确，也只保护特定边界内的数据。先问密钥在哪里、明文在哪里出现、攻击者控制哪一层，才能判断加密是否解决了真正的问题。

| 加密位置 | 主要保护的场景 | 通常仍能看到明文的一方 |
| --- | --- | --- |
| 磁盘或整盘加密 | 设备关机后磁盘被盗、离线读取介质 | 已解锁的操作系统和应用 |
| 数据库或存储服务加密 | 存储介质、快照或备份泄漏，具体效果取决于密钥是否分离 | 获授权的数据库或服务 |
| 应用层字段、文件加密 | 数据离开应用后的存储暴露，前提是密钥在另一边界管理 | 执行加解密的应用 |
| 传输加密 | 网络途中被窃听或修改 | 通信两端 |
| 端到端加密 | 中间传输与服务提供者读取内容，具体取决于密钥和终端设计 | 通信端点 |

例如，数据库启用了磁盘加密，不表示攻击者拿到应用的数据库账号后看不到查询结果；TLS 保护网络传输，也不表示接收端不会把明文错误地写入日志；应用层加密若把密钥与密文保存在相同权限下，对部分泄漏场景帮助有限。加密层级不是越多越好，每一层都应对应明确的威胁。

认证加密也不会判断业务内容是否真实。一份经过合法程序加密的错误配置仍会通过验证；获得密钥的攻击者也能产生合法标签。AEAD 提供的是密码学意义上的保密性与完整性，输入是否合法、操作者是否获授权、旧数据是否允许恢复，仍由应用和密钥管理制度决定。

## 5.9　回到最初的问题

开头的问题是：存储中的密文别人看不懂，是否就不会被悄悄改变？现在可以给出完整回答：

1. 加密首先解决保密性，不能据此推断一定具有完整性。
2. 应用通常应使用成熟 AEAD 方案，使密文和 AAD 的改变在解密时导致失败。
3. 认证标签可以公开保存，但不能被截断、忽略或用普通哈希代替。
4. Nonce 必须遵守具体算法的使用规则；标签不会挽救 Nonce 重复。
5. 验证成功不等于拥有业务权限，也不表示消息没有被重放。
6. 加密只覆盖设计好的边界，终端、密钥和合法应用仍可能接触明文。

看到“数据已经加密”时，应继续问：使用的是否是认证加密？Nonce 怎样管理？哪些字段进入 AAD？标签失败时会怎样？密钥与密文是否处于不同的权限边界？这些问题比只问“用了 AES-128 还是 AES-256”更接近系统实际会不会失守。

## 练习

1. 一个程序用某种只提供保密性的方式加密配置文件，解密后若 JSON 能解析就直接使用。为什么“能解析”不能证明文件未被攻击者修改？
2. 某条记录的密文与标签都没有变化，但攻击者把它复制到另一个文档编号下。怎样使用 AAD 让这种调换被发现？
3. 标签验证失败后，程序仍把已经产生的部分明文交给图片解析器。这样做有什么问题？
4. 两次 AES-GCM 加密使用相同密钥和 Nonce，但每次都生成了认证标签。标签为什么不能使这种做法安全？
5. 数据库磁盘已经加密。攻击者取得正在运行的应用所用数据库账号后，是否一定看不到查询结果？这说明设计前还要明确什么？
6. 一条旧密文及其 Nonce、AAD 和标签被原样恢复，验证成功。这能否证明它是当前允许使用的最新版本？

### 参考答案

1. 格式校验只检查数据能否被解析，不验证数据是否由持有密钥的一方产生，也不能可靠发现所有修改。攻击者可能造成仍然合法但含义变化的结果。
2. 加密时把文档编号以及必要用途纳入 AAD；解密时从当前记录重建相同 AAD。密文被搬到其他编号后，AAD 不同，标签验证应失败。
3. 在整条消息认证完成前，这些字节不可信。解析器可能基于攻击者控制的内容执行操作、暴露错误差异，或提交部分结果。
4. 重复的密钥与 Nonce 会破坏 AES-GCM 赖以提供保密性和完整性的前提；标签本身也由这套已被错误复用的机制产生，无法补救。
5. 不一定。磁盘加密主要保护离线介质；已获授权的运行中应用和数据库仍需取得明文。设计时要明确攻击者位置、密钥位置和明文出现的边界。
6. 不能。它只能说明这套输入在密钥下通过密码学验证。旧版本是否仍有效，需要另外的版本、状态或防回滚机制判断。
