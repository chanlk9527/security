# 第 4 章　哈希、MAC 与密码存储：同样是摘要，为什么不能互换

你从网站下载了一个安装包。网页同时列出一串 SHA-256 值。计算机算出了相同的值，文件就一定安全吗？稍后，你的服务收到一条带“签名”的回调，验证通过后就可以放心执行吗？最后，用户注册账号时，既然密码也能算 SHA-256，为什么不能只存这个结果？

这三个问题表面上都在“把一段数据变成另一段较短的数据”，要防的失败却不同。本章按问题出现的顺序阅读：先弄清普通哈希能说明什么，再看需要证明消息来自谁时为什么引入 MAC，最后讨论人选的密码为什么需要一套更慢的验证机制。每学到一种工具，都要追问它没有解决哪一种攻击。

## 4.1　第一步：下载的文件有没有变

安装包可能在传输、复制或保存时受损。如果发布方预先公布一个摘要，下载者就可以对收到的文件再算一次，比较两个结果。密码学哈希函数就是做这件事的基础工具之一：它接收任意长度的**字节序列**，给出固定长度的摘要。同一算法处理完全相同的字节，结果总相同；哪怕只改动一个字节，结果通常也会大幅变化。

以 SHA-256 为例，其摘要长度是 256 位，也就是 32 字节。网页上常见的 64 个十六进制字符只是这 32 字节的一种写法，并不意味着摘要本身有 64 字节。文件名、扩展名和“看起来一样”的文本都不是比较依据；输入必须是约定好的**实际字节**。例如一份文本在不同换行方式或编码下，肉眼看到的字可能一样，哈希结果却可能不同。

计算并比较摘要，能回答的是：“我拿到的文件，是否与这串已知摘要对应的文件一致？”它没有回答“这串摘要是谁给我的”。若只想发现一次意外传输损坏，网页上的摘要已经有用。若担心攻击者控制下载页，他完全可以同时换掉安装包和页面上的摘要，让比较仍然通过。此时缺的不是更长的摘要，而是**可信的摘要来源**。事先共享秘密的双方可以使用后面讨论的 MAC；面向许多公众下载者的发布场景，通常更适合使用[数字签名](https://csrc.nist.gov/pubs/fips/186-5/final)。这些机制如何建立可信关系，不能靠普通哈希单独完成。

[NIST 的安全哈希标准](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)描述了用于生成消息摘要的算法。这里先记住哈希最基本的行为：**同样的输入得到同样的摘要；任何人拿到输入都能自行计算。**后一句正是它不能单独证明发布者身份的原因。

## 4.2　“内容一致”到底依赖哈希的什么性质

摘要长度固定，而可能的文件远多于可能的摘要，因此不同文件最终出现相同摘要在逻辑上不可避免，这叫**碰撞**。安全设计不要求碰撞绝对不存在，而要求攻击者在现实成本内难以有意找到可利用的碰撞。还要区分两个相近的问题：已知某个文件及其摘要，能否找出另一个具有同样摘要的文件；只知道一个目标摘要，能否找出某个与之匹配的输入。它们分别涉及第二原像和原像攻击，难度与用途并不完全相同。

作为入门读者，不必先计算这些攻击的复杂度，但要知道“哈希值很长”不是选算法的全部理由。用来抵抗有意篡改时，应选择当前仍被认可的密码学哈希算法，并明确自己依赖的是哪种抗攻击性质。应用里常见的普通哈希表函数或校验和，可能很适合快速分桶或检测随机差错，却不能自动代替密码学哈希。

“哈希难以反推”也经常被误解。假设摘要来自随机产生、候选空间极大的文件或密钥，寻找对应输入可能很难；若输入是“123456”一类人选密码，攻击者无需逆向破解算法，只要计算常见候选值并逐一比较即可。**算法对任意输入的单向性，不会把本来容易猜的输入变得难猜。**这个区别稍后会决定密码如何存储。

### MD5：一个具体的旧算法

MD5 曾广泛用于生成文件摘要，输出长度为 128 位，因而在旧下载页面和旧系统中仍会看到它。它的问题不只是输出比 SHA-256 短：攻击者已经能够构造**内容不同、MD5 摘要相同**的输入。若某种安全判断依赖“不同内容很难有同一摘要”，MD5 就不再合适，例如不能用于需要抗碰撞能力的数字签名。[RFC 6151](https://www.rfc-editor.org/rfc/rfc6151)明确区分了这种用途与单纯检测传输差错的用途。

这里也要避免反过来讲过头。能构造一对碰撞文件，不等于能对任意一份**已经固定**的文件轻易找出相同 MD5 的替代品；后者是前面说的第二原像问题。如果旧流程只用 MD5 检测偶然损坏，它仍能发挥校验作用；但面对恶意篡改，新设计不应拿它提供抗碰撞保证。即使用 SHA-256，若攻击者能同时替换文件和网页上的摘要，也仍不能证明发布者身份。**算法的安全性质与参考摘要的可信来源，是两个独立问题。**

MD5 也不适合直接保存密码，因为它计算很快，数据库泄漏后方便攻击者大量试猜。HMAC-MD5 则是另一种带密钥构造：普通 MD5 的碰撞问题不等于现有 HMAC-MD5 都能被直接伪造，但 [RFC 6151](https://www.rfc-editor.org/rfc/rfc6151)仍建议新协议不要选用它。这些边界比记住“MD5 已过时”一句口号更有用。

## 4.3　第二步：消息是谁发的

现在换一个问题。某服务收到一条“订单已支付”的回调。攻击者也能写出这几个字，并计算它们的 SHA-256 摘要。接收方即使发现消息与摘要相符，也无法判断发送者是不是合作方：普通哈希的计算方法是公开的，任何人都能为自己编写的消息附上正确摘要。

要证明消息来自有资格的一方，发送方和接收方可以预先共享一把只有他们知道的**密钥**。发送方用密钥和消息生成校验值，接收方用同一密钥验证。没有密钥的攻击者可以改写消息，却应难以为改写后的消息生成合法校验值。这类机制叫**消息认证码**，简称 MAC。它比普通哈希多回答了一个问题：“生成校验值的人是否掌握约定的密钥？”

但请留意措辞：验证通过，只能把消息归于**某个密钥持有者**，不能证明现实中究竟是谁操作了发送端。密钥一旦泄漏，攻击者也能生成合法校验值。MAC 不负责隐藏消息内容；接收方和发送方都掌握同一密钥，因此它也不能向第三方证明“只有发送方可能生成它”。需要第三方独立验证时，应再看数字签名。

## 4.4　HMAC 是 MAC 的一种做法

MAC 是一类机制的名称，**HMAC** 是其中一种标准构造：它利用密码学哈希函数和共享密钥生成消息认证码。例如 HMAC-SHA-256 用到了 SHA-256，但它不是普通的 SHA-256(消息)，也不是随意把密钥拼到消息前后再做哈希。使用时应调用成熟库的 HMAC 接口，无须在基础手册里推导其内部公式。[NIST 的 HMAC 标准](https://csrc.nist.gov/pubs/fips/198-1/final)给出了正式定义。

拿 Webhook 想象一次完整交互。服务 A 向服务 B 发一段事件消息，并附上用共享密钥算出的 HMAC。B 用同一密钥对约定的消息内容重新计算：若攻击者把“待支付”改成“已支付”，原校验值便不再匹配；若攻击者没有密钥，也难以为改过的消息补出新值。[GitHub 的 Webhook 验证文档](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)提供了一个实际使用共享秘密校验消息的例子。这里真正要理解的是**密钥把校验值与有资格的发送者联系起来**，而不是记住某个 HTTP 头的名字。

还有一道边界：攻击者若原样复制一条过去的真实消息及其 HMAC，再发送一次，校验依然可能通过，因为字节并未改变。这叫**重放**。接收方要根据具体协议检查消息的新鲜性，并避免同一事件重复产生业务结果。HMAC 证明的始终是“受保护的内容与密钥持有者有关、内容未被改动”，不自动证明“这件事第一次发生”或“消息陈述的业务事实一定真实”。

实现时还必须清楚哪些字节参与了计算：若只认证请求体，就不能假定未包含的请求头也可信。原始字节、密钥保管和安全比较等细节，应按具体服务协议与密码库文档落实；它们不改变这里的核心判断。

## 4.5　第三步：密码也有摘要，为什么不能照搬 SHA-256 或 HMAC

用户注册时，系统需要保存某种验证记录，以便以后判断登录者输入的密码是否正确。若保存明文，数据库泄漏就等于直接交出所有密码；若改成直接保存 SHA-256(密码)，攻击者拿到数据库后仍可以在自己的机器上猜测。他不受登录接口限速约束，只需对“123456”“常见短语”等候选值高速计算 SHA-256，与库中的摘要比较。普通哈希设计得快，在这里反而帮了攻击者。

给密码加一个每条记录独立的**盐**，能让相同密码形成不同验证结果，使一份预先算好的候选摘要不能直接匹配所有用户；盐通常与结果一起保存，不要求保密。但盐没有改变某条记录中弱密码本身容易猜到的事实。对着这条记录，攻击者仍能用已知盐逐个试候选。要提高这一步的成本，必须用**专用密码哈希方案**，让每次猜测消耗可调整的计算资源。上一章已经解释盐为什么出现；即使从本章开始阅读，也只需记住：盐解决“跨记录复用猜测成果”，成本参数解决“每次猜测太便宜”。

这类算法和普通 SHA-256、HMAC 的目标不同。文件摘要和消息认证通常要足够快，才能处理大量数据和请求；密码验证发生的次数相对少，可以有意让一次验证付出合理成本。成熟方案包括 Argon2id、scrypt，以及特定约束下使用的 PBKDF2；已有系统也可能使用 bcrypt。新系统应按当时的权威指南和平台条件选择，不要用“SHA-256 重复算很多遍”自行拼装。Argon2id 等方案还可使用内存成本，让攻击者大规模并行猜测更昂贵。[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)解释了算法选择、盐与工作参数。

也不要把 HMAC 的密钥当成密码存储的完整答案。即使服务端另有一把共享秘密，用户密码仍可能很弱；一旦威胁模型变化或秘密泄漏，快速验证记录仍可能被批量猜测。额外的服务器秘密有时可作为分层防护，但它需要单独的密钥管理，并不能代替每条记录的盐和专用密码哈希。把用户密码可逆加密后保存通常也不合适：一旦解密密钥泄漏，原密码可以被成批还原，而登录验证本来不需要取回原文。

## 4.6　从注册到升级：验证记录怎样活下去

注册或修改密码时，应用先检查新密码是否属于已知常用、易猜或泄漏的密码，再交给成熟密码哈希库生成验证记录。记录通常包含算法标识、参数、盐和结果；密码明文不应写进数据库、日志或监控。登录时，应用把用户输入交给库的验证接口，由库根据记录中的算法、参数和盐检查是否匹配。不要自己从记录中拆出一串字符，再用普通字符串比较来“复刻”库的验证逻辑。

参数不是写一次就永远不变。设备性能会变，攻击者的计算能力也会变；验证记录保留算法和成本信息，才能在用户下次成功登录时判断是否需要重新生成更强的新记录。尚未登录的账号不会自动完成这种升级，旧记录如何处理需要明确策略，必要时要求重置密码。迁移时还要保留识别旧格式的能力，并规划何时退出旧方案；不能仅把数据库里的旧摘要改个字段名，就声称密码已升级。

密码哈希保护的是**数据库泄漏后的离线猜测成本**。有人直接在登录页面反复试密码，属于在线猜测，应由账户或设备维度的限速、异常检测等机制处理；常见密码拦截则尽量减少一开始就容易猜中的密码。[NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)同时强调抗离线攻击的加盐密码哈希、常见密码拦截与失败尝试限速。三者面对不同阶段，不能互相代替。

选择成本参数时也不能只求越慢越好。合法登录要消耗同样的 CPU 和内存，过高成本可能拖慢服务，甚至放大拒绝服务风险。应使用库支持的方案，在目标机器上测量验证延迟和并发负载，依据当前指南设定并定期复核。这里不给出永久有效的一组数字，因为参数必须随平台、流量与最新建议调整。

## 4.7　回看三个问题

| 要解决的问题 | 应用的机制 | 验证者需要什么 | 不能顺带得到什么 |
| --- | --- | --- | --- |
| 文件是否与可信摘要对应 | 密码学哈希 | 可信的参考摘要 | 摘要发布者的身份、内容保密 |
| 消息是否由共享密钥持有者生成且未改动 | MAC，例如 HMAC | 同一把秘密密钥、明确的受保护字节范围 | 第三方可验证的署名、自动防重放、内容保密 |
| 数据库泄漏后，密码是否难以被批量猜出 | 专用密码哈希 | 独立盐、合适参数与验证记录 | 在线限速、强密码选择、账号恢复安全 |

面对新需求，不要先问“该不该用 SHA-256”，先问攻击者能控制什么：他能同时改文件和网页吗？能伪造请求却拿不到共享密钥吗？能拿到整份密码数据库并离线试错吗？威胁不同，哪怕最后都看到一串像摘要的字符，应该使用的机制也不同。

## 练习

1. 下载站把安装包和 SHA-256 值放在同一网页。攻击者能修改整个网页及下载文件。用户算出的摘要一致，能否据此认定安装包来自原发布者？缺少什么？若换成 MD5，还要额外担心什么？
2. A 与 B 共享一把密钥，用 HMAC 校验双方消息。旁观者 C 能看到消息和校验值，却不知道密钥。C 改写消息后，为什么不能只计算一个普通 SHA-256 摘要来通过验证？B 又能否向第三方证明“这条消息只能是 A 生成的”？
3. 一条支付回调连同 HMAC 被原样发送两次，两次校验都通过。第二次一定是伪造的吗？怎样避免同一事件重复改变业务状态？
4. 数据库保存了 SHA-256(盐＋密码)。每人盐都不同，为什么还不能认为密码存储已经安全？
5. 一个旧系统把 SHA-256 密码摘要直接标记为“Argon2id”，没有重新计算。迁移真正需要什么时机和信息？

### 参考答案

1. 不能。攻击者可同时替换文件和参考摘要；需要从可信渠道取得摘要，或用能够验证发布方凭证的机制认证发布内容。换成 MD5 还要考虑它已不能为需要抗碰撞的场景提供可靠保证；但这与“参考摘要本身不可信”是两个不同问题。
2. B 验证的是带共享密钥的 HMAC，普通 SHA-256 摘要即使与新消息相符，也不能代替它。B 自己也持有密钥、能够生成合法 HMAC，因此不能仅凭该值向第三方证明只能由 A 生成。
3. 不一定，可能是正常重试，也可能是旧消息被重放。应依协议判断事件是否仍有效，并识别已处理事件，使同一事件只产生一次应有的状态变化。
4. 盐阻止跨记录复用候选结果，但 SHA-256 计算太快，攻击者仍可用每条记录的盐高速离线猜测弱密码；需要专用密码哈希与适当成本。
5. 改标签不改变旧摘要的安全性质。应保留旧格式识别，在用户输入正确密码时用新算法、参数和盐重建记录；长期不登录的账号需另定重置或清理策略。
