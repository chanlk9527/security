# 第二部分导读：密码学的工程基础

密码学很少以“算法本身不够强”的方式出现在应用事故中。更常见的情况是，系统把需要保密的东西拿去做了哈希，把只需要唯一的值当成了秘密，验证了签名却没有验证签名者，或者保护了传输链路却没有处理密钥的生命周期。本部分不展开完整的数学推导，而是帮助你在这些工程边界上做出准确判断。

## 先说明全书编号

这里的“第二部分”不是“第 2 章”。全书的章节编号是连续的：第一部分已经包含第 1 章和第 2 章，分别讨论安全目标、资产、威胁、攻击故事和信任边界。因此，密码学部分从第 3 章开始，依次到第 7 章；01 和 02 没有缺失，也不需要在本部分前补写。这个文件是第二部分的导读，不占用章节编号。

## 本部分要建立的判断

读完本部分，你应当能够回答以下问题：

- 一个值需要不可预测、需要保密，还是只需要在规定范围内唯一？
- 哈希、MAC、加密和数字签名分别提供什么保证，又没有提供什么保证？
- 密码存储为什么需要专用的慢哈希和盐，而不能直接套用普通摘要？
- 加密为什么还要同时处理完整性、关联数据和 Nonce 重用？
- 公钥可以公开以后，系统凭什么把它和某个主体或域名联系起来？
- TLS 保护的是哪一段连接，证书、密钥和会话又如何继续影响实际安全性？

这些问题会反复把我们带回同一个原则：先说明要证明的性质，再选择能提供该性质的机制。名称相近的技术不代表可以互换，算法成功运行也不代表业务目标已经实现。

## 建议的阅读方式

建议按章节顺序阅读，因为后面的章节会复用前面建立的词汇：先理解一次性值和秘密，再区分摘要、完整性与保密，之后才更容易看懂公钥协议和 TLS。每章都可以独立查阅；如果你是为了排查一个具体问题，可以先从章节标题中对应的机制进入，再回到前一章补足前提。

阅读时不要只记住“应该使用某某算法”。请同时写下三件事：系统要保护或证明什么、攻击者能控制哪一部分输入、控制失效后系统如何发现和止损。具体算法、参数和产品配置会随标准和平台更新，实施时仍应核对当前规范与平台文档。
