# 第一部分导读：安全目标、威胁与设计原则

## 为什么从“怎样描述问题”开始

软件安全不是在功能完成后加上的一层装饰。一次登录、一次文件下载、一个后台任务，都会让系统根据某些信息决定“谁可以对什么做什么”。如果连需要保护的对象、可能造成的损失和允许行为都没有说清楚，后面的加密、认证、权限控制和监控就很难判断是否真的解决了问题。

本部分先处理安全工作的共同起点：把模糊的安全愿望变成可以讨论、实现和验证的要求。我们不从某个产品或漏洞分类出发，而是从一个具体功能出发，逐步回答四个问题：系统承载了什么价值？系统在哪些位置作出信任判断？攻击者能怎样让这些判断失效？应该把控制放在哪里，又用什么证据证明控制有效？

这四个问题对应四种经常被混淆的工作。识别资产不是列出所有数据库表，而是说明哪些内容、关系、凭据和服务能力一旦受损，会给谁带来什么后果；寻找信任边界不是画一张漂亮的架构图，而是找出请求、身份、数据和权限在组件之间交接的地方；威胁分析不是罗列攻击名称，而是明确攻击者前提、攻击路径、影响范围和优先级；选择控制也不是堆叠产品，而是让每项控制对应一个要求，并留下能够复核的验证证据。

## 四章怎样连成一条分析流程

四章按“目标 → 判断 → 威胁 → 控制”的顺序组织。第 1 章先建立资产、损失、安全目标和验收要求，回答“要保护什么”；第 2 章沿着数据流和权限流跟踪一次请求，回答“系统凭什么相信某个身份、对象或状态”；第 3 章把这些判断放到攻击者能够观察、篡改、重放或取得凭据的条件下，形成攻击故事并判断风险；第 4 章再根据风险选择预防、检测、响应和恢复措施，明确控制位置、责任人、证据和剩余风险。

这种顺序也说明了各章的边界。没有第 1 章的目标，威胁清单容易变成与业务无关的漏洞目录；没有第 2 章的边界，攻击故事会停留在抽象的“黑客入侵”；没有第 3 章的前提和影响，控制选择无法排序；没有第 4 章的验证，安全要求就无法进入开发、测试和运行流程。读完本部分，读者应能把一个功能整理成一套可交接的安全分析资料，而不是只记住若干原则的名称。

## 贯穿案例：从一次分享请求看完整系统

四章使用同一条云相册案例作为主线。相册主人邀请朋友查看和下载旅行照片，同时还要保护未分享的私人照片、照片归属、邀请与分享关系、账号控制权和操作记录。这个场景会逐步扩大：先定义分享承诺，再跟踪一次查看原图的请求，接着加入缩略图生成等后台任务，最后讨论攻击者如何利用错误的身份绑定、对象引用、旧链接、重放或服务权限扩大影响。

案例中的人物和组件会承担不同的角色：相册主人和受邀朋友是业务主体，其他用户代表未授权访问者，相册服务负责作出业务判断，数据库和对象存储保存不同类型的数据，后台任务以独立的服务身份运行。这样安排是为了让“主体、资源、动作、条件、证据”始终落到同一个系统里，而不是在抽象定义之间来回切换。

## 阅读本部分时要留下什么

建议不要只把本部分当作概念导读。可以选一个自己熟悉的功能，例如文件分享、导出报表或重置密码，随着章节推进同步记录：

1. 功能依赖哪些资产，哪些副本和关联记录也必须纳入保护范围？
2. 每个主体在什么条件下能对哪个资源执行什么动作？
3. 请求经过哪些组件，哪些信息被当作身份、归属、格式或状态的依据？
4. 攻击者需要哪些前提才能改变结果，影响会扩散到哪些资产？
5. 哪项控制负责降低风险，怎样通过允许、拒绝、失败、撤销和恢复场景验证它？

每章结束时，把答案整理成一份可以交给开发、测试和运维共同使用的材料。后续密码学、身份权限、应用安全和安全运行章节会反复引用这些材料，并在具体机制中补充实现条件。

## 建议的阅读方式

先用一个熟悉的功能列出资产和损失，再画数据流与信任边界，随后明确攻击者能力并组织攻击故事，最后选择控制与证据。具体机制将在后续章节展开，本部分先建立分析和判断的方法。
